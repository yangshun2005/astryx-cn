# 集成贡献描述符系统规范

## 意图

Astryx 集成贡献的每个可发现项，都在其所描述项旁边有一份本地、强类型的描述。贡献者无需编辑包内其他位置的第二份目录，即可理解、编写、校验、移动和打包单个项。

规范描述符为 `<source-stem>.doc.mjs`。它是逐项元数据的唯一来源。集成清单定位贡献根并持有集成级能力；它不编目根下的项。任何形式、任何位置都不存在项的中心目录（FR11）：0.6 曾误为主题发布过一个，后来不得不作为破坏性变更移除。

## 非目标

- 在正常的破坏性变更与迁移流程允许之前，移除已发布的兼容读取器。
- 将 `debug` 或 `gapReport` 等运行时集成特性变为项贡献。其类型化命名导出契约仍归 `spec:AST-031` 所有。
- 将构建回执、生成的输出清单或消费者运行时数据放入编写描述符。
- 要求引用文档（其 `.doc.mjs` 本身即完整载荷）另有一个可执行源文件。
- 在发现期间执行贡献的源码以获知其元数据。

## 需求

- **FR1 — 每个可发现项拥有一份规范描述符。** 新增或新编写的组件、模板、主题、文档主题、codemod 或未来的项贡献，必须有且仅有一份 `<source-stem>.doc.mjs` 描述符。当该项有主源文件或载荷文件时，描述符必须位于其旁边且必须使用相同的主干名。引用文档既是描述符又是载荷。
- **FR2 — 描述符是强类型的编写模块。** 每种描述符类型必须从 `@astryxdesign/cli/authoring` 导出公开的 TypeScript 类型，在 JSDoc 注解中使用该类型，并通过该类型的规范导出（新描述符类型为带标记的默认导出）暴露其值。发现必须在加载边界通过该类型的公开编写解析器解析已加载的值。新类型若缺少其类型、解析器、自文档和解析器测试，即为不完整。
- **FR3 — 描述符是逐项元数据的唯一权威。** 逐项名称、标签、描述、就绪或维护状态、源关系及复制元数据，不得在根 JSON 目录、`astryx.integration.*` 中的数组或其他包级注册表中重复。集成清单可以定位根并声明集成级元数据或运行时能力。它不得枚举根下的项。逐项选项（如 `replaces` 和 `extends`）属于该项自己的描述符。
- **FR4 — 配对身份是结构性的。** 当该关系是结构性的时，发现必须从共享的描述符/源主干名推导主源路径及任何源绑定的运行时导出身份。描述符拥有稳定的公开项身份。组件描述符的 `name` 是其记录的运行时导出：当同主干源没有以该主干名命名的运行时导出时，该 `name` 可以命名该源的另一运行时导出，发现以该名称记录该组件。组件描述符在 `components` 中列出的每个完整条目，当描述符的 import 所命名的模块导出它时，即为以其自身名称命名的组件。当打包生命周期写入该 import 所命名的文件时，`integration verify` 按发现于打包后列出的成员比较该描述符的成员。每个表面（FR7）按这些名称列出、查找并校验这些组件，导出其主干名的源保留该主干名。仅以此方式记录的发现名称，不得占用 Core、旧版文档包或以源命名的组件所应答的精确无作用域查找，而以另一名称记录的描述符的主干名，同样让位于 Core 和以源命名的组件：此类查找返回该所有者的组件，除非声明的替换认领该名称，限定于该包的查找返回该包的组件，且 Doctor 报告 Core 共享的记录名称。精确名称（包括以此方式记录的发现名称）优先于 Core 的关键字回退。发现必须拒绝缺失源、多于一个符合条件的同主干源、无效的推断导出名，或编写身份与其所需目录身份冲突的描述符。当模板的显示名包含其所展示组件的每个词时，该模板也应答该显示名；仅变体标签则不然。
- **FR5 — 多文件项有一个受限的所有权边界。** 项需要嵌套源、令牌、调色板、资产或回执文件的类型，必须定义一个项本地复制与打包边界。发现和编写必须在不使用第二份目录的情况下枚举该边界，保持每条路径位于其内，并复制完整的所属集合。缺失的本地依赖、逃逸的路径和意外的符号链接目标，必须在消费者写入之前失败。
- **FR6 — 发现不执行贡献的载荷源码。** 加载描述符遵循既定的文档模块边界。可执行的组件、主题、模板和 codemod 载荷，必须在发现期间检查或解析而不运行它们。当运行时绑定是契约的一部分时，静态校验必须拒绝仅类型或缺失的运行时导出。
- **FR7 — 单一发现接缝服务于每个下游表面。** 列出、包所有权、歧义处理、编写校验、Doctor、包清单、打包消费者校验和物化，必须消费同一份规范化发现记录。写入者必须通过该接缝校验其输出，而非重新实现格式。
- **FR8 — 编写只产出规范形式。** `astryx integration add` 及其类型化 API 必须写入 `.doc.mjs`、公开 JSDoc 类型注解和约定导出。它们不得创建新的旧版别名、中心项目录、无类型对象或重复的元数据源。
- **FR9 — 已发布的别名是兼容输入，而非编写先例。** 在兼容策略要求期间，读取器可以保留已发布的替代后缀或组合模块。新写入者和示例必须使用规范描述符。每个保留的别名必须隔离、作为兼容路径测试，并排除在新贡献类型的设计之外。仅金丝雀格式无兼容性主张。
- **FR10 — 主题注册是首个干净的应用。** 主题根为每个小写 kebab 短名包含一个目录。该目录包含一个主题源和必需的相同主干 `.doc.mjs`。`ThemeDoc` 拥有 `name`、`displayName`、`description` 和 `maintained`；源入口和命名运行时导出来自共享主干名。该目录是递归复制与打包边界。`themes/manifest.json` 不得保留为回退读取器。该目录随稳定版 `0.6.3` 发布，因此其移除是破坏性变更：它随一个 codemod 在次要版本中发布，该 codemod 将每个目录条目转换为该主题的描述符，仍持有该目录的主题根会失败并给出指明迁移的消息。
- **FR11 — 绝不中心编目项。** 任何变更不得为任何类型添加：根下列出该根项的文件（`themes/manifest.json`、`components/index.json` 或类似文件）、`astryx.integration.*` 中的逐项映射或列表（例如模板替换映射或主题列表），或作者手工保持同步的注册表。添加一个项不得改变其同级共享的文件；只有集成清单和 `package.json` 可以改变，以声明新根。审查必须拒绝添加中心目录的变更，写入者测试必须在其上失败。
- **FR12 — 文档化的组件 Props 与源一致。** 受 `architecture:cli-surface` INV33 管辖。
- **FR13 — 每个描述符满足其发布的编写类型。** 受 `architecture:cli-surface` INV34 管辖。
- **FR14 — 一条命令检查集成，并可门控其构建。** 受 `architecture:cli-surface` INV35 管辖。

### 兼容性过渡

最终规则适用于每种类型。现有已发布输入迁移至该规则，而不假装它们从未发布：

- 组件和引用文档已使用 `.doc.*`；新编写收窄为强类型 `.doc.mjs`，而已发布后缀仍可读；
- 模板保留其已发布的 `.template.*` 读取器，但新编写和示例使用已支持的 `.doc.mjs` 配对；
- 主题替换 JSON 目录（发布于 `0.6.3`）作为破坏性变更：无双读取器，codemod 转换每个包；
- 组合 codemod 模块和内联 `agentDocs` 在配对描述符迁移发布前仍为已发布兼容输入；它们不允许其他贡献类型省略描述符。

## 当前状态影响

本规范拥有一个当前系统规范未覆盖的独立边界。`spec:AST-031` 明确排除默认清单项贡献，而 `architecture:cli-surface` 描述实现但无法授权新的跨类型编写规则。

本规范以每个主题一份强制描述符替换 `architecture:cli-surface/INV19` 中的目录主张。它为 CLI 架构和贡献者清单添加通用描述符不变量。主题变更更新公开编写类型、发现、捆绑资产、集成编写、包清单、打包校验、消费者文档和真实提供者到消费者测试。

该契约不改变 `DefineThemeInput` 或 `DefinedTheme`。主题包元数据保持在 Core 运行时编写之外，与 `architecture:theme-authoring-contract/INV11` 一致。

## 决策日志

### DEC-1 — 每个贡献项使用一份类型化同主干描述符

**参考：** `spec:AST-039/DEC-1`
**决策者：** `joeyfarina`，`2026-09-12`

贡献的描述属于其所描述的源或载荷旁边。一份类型化模块为编辑器和 CLI 提供相同契约，使项可作为单元移动，并防止根目录偏离源。集成清单保持为根定位器和集成能力边界。

拒绝：中心 JSON 目录。它创建仅主题的编写语言，重复源身份，并允许 CLI 接受不遵循仓库 `.doc.mjs` 约定的格式。

拒绝：在 JSON 目录之上叠加可选描述符。两个元数据源需要优先级和漂移规则，并保留设计缺陷。

### DEC-2 — 推断主题源身份并拥有整个主题目录

**参考：** `spec:AST-039/DEC-2`
**决策者：** `joeyfarina`，`2026-09-12`

主题源和描述符共享一个主干名。该主干名标识入口和必需的命名运行时导出。小写 kebab 父目录和 `ThemeDoc.name` 在 CLI 短名上一致。完整主题目录（包括其描述符）是复制与打包边界，因此嵌套文件无需编写的允许列表。

拒绝：将 `entry`、`exportName` 和 `files` 前向带入 `ThemeDoc`。这些字段重述发现可直接证明的结构，并在每个文件内重建目录。

### DEC-3 — 保留已发布读取器而不削弱新编写

**参考：** `spec:AST-039/DEC-3`
**决策者：** `joeyfarina`，`2026-09-12`

稳定版 `0.6.0` 已读取早于本规则的模板、codemod 和内联 agent 指南形式。兼容读取器保留至其正常迁移路径允许移除。所有新写入者和新贡献类型立即使用规范描述符。主题目录（误随稳定版 `0.6.3` 发布）不获得兼容读取器；它作为破坏性变更随 codemod 移除（DEC-4）。

拒绝：将每种历史形式视为永久同等约定。为兼容而保留的读取器不定义编写系统接下来应创建什么。

### DEC-4 — 任何类型均无中心目录或清单映射

**参考：** `spec:AST-039/DEC-4`
**决策者：** `joeyfarina`，`2026-09-24`

`integration add theme` 在 0.6 中写入的主题目录是个 bug：它将逐项细节放入一个中心文件，违背其他每种类型遵循的规则。它在任何人发现之前到达稳定版 `0.6.3`。它作为破坏性变更移除，随一个转换每个包的 codemod，且 FR11 现在彻底禁止该模式，以免任何类型重复它。

这取代 `spec:AST-035/DEC-1`，后者是保留模板替换为集成清单中映射的草案：模板的 `replaces` 属于其自己的描述符。

拒绝：仅为替换的清单映射。它是同一个中心目录，一次一个字段。
