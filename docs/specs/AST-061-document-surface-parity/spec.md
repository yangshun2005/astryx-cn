# Markdown 文档界面一致性系统规范

<!-- 描述系统本身，而非项目：用现在时，说明它做什么。记录中不写提案、历史、Pull Request 或调研；参见 docs/contributing/spec-writing.md，并在 Pull Request 中报告其评分结果。 -->

## 意图

当核心 `Markdown` 与 RichText 界面 `RichTextEditor`、`RichTextView` 展示同一份 Markdown 文档时，读者看到的是同一份文档：每个界面上的排版、块间距、行宽、结构和方向都相同。产品在同一位置切换阅读与编辑该文档时，切换不移动任何块相对其他块的位置，也不重排任何行；只有编辑控件出现或消失。

## 非目标

- 字节级相同的 DOM。只要渲染结果和语义一致，各界面保留自己的标记。
- Markdown 方言本身，以及 RichText 导入导出 Markdown 源文本的方式。本记录规定受支持的结构渲染后的外观和含义，不规定由哪段源文本产生、源文本如何往返。唯一例外是 DEC-5 共享的字符引用解码器。
- 协作、持久化、文档托管，以及 Markdown 插件与编辑器之间的插件适配器。
- 产品编辑整篇文档时选用哪个编辑器引擎，以及产品存储什么值。本记录规定各界面如何渲染同一份文档；RichText 自身的角色和值见 DEC-7。
- RichText 的发布通道。由包的发布通道元数据决定（spec:AST-033 FR4），升级遵循 spec:AST-017 FR23；本记录不涉及。
- 满足本契约的等价内部实现仍然有效，但字符引用解码器除外，DEC-5 将其定为唯一的共享公开函数。

## 需求

- **FR1 — 由一份契约裁决，而非任一渲染器。** 当 `Markdown` 与 RichText 界面对同一受支持内容不一致时，由 CommonMark 语义裁决含义，由共享的字号阶梯、间距和颜色令牌裁决呈现。任一面界的当前输出都不是基准：不一致按契约判定为错误的一侧修复，该侧可能是 `Markdown`。
- **FR2 — 排版相同。** 正文使用 `--text-body-size` 和 `--text-body-leading`；标题级别 N 使用 `--text-heading-N-size`、`--text-heading-N-weight` 和 `--text-heading-N-leading`，并采用标题字体族，级别 1–6 均如此。粗体文本使用 `--font-weight-semibold`。行内代码在每个界面上使用相同的 chip 尺寸、字体族和内边距。
- **FR3 — 块间距相同。** 块之间按每种密度一张间距表分隔。默认密度：标题 1–3 前 `--spacing-6`、后 `--spacing-3`；标题 4–6 前 `--spacing-4`、后 `--spacing-2`；段落和列表两侧均为 `--spacing-3`；围栏代码、引用块和表格为 `--spacing-4`；分隔线为 `--spacing-6`。紧凑密度使用同一张表的紧凑列。首块的前外边距和末块的后外边距为零。
- **FR4 — 行宽相同。** 散文块的最大内容宽度相同，默认 `680px`；宽块（围栏代码、表格）在每个界面上都占满可用宽度。
- **FR5 — 结构相同。** 段落的软换行合并为一行流式文本；硬换行断行。引用块中的各行延续为一个段落。有序和无序列表按 CommonMark 缩进嵌套，每项显示一个标记，标记样式随深度变化（DEC-6）。无序列表在每一层嵌套都保留相同的主题内缩。每个列表内，阅读方向相同的同级项共享同一条行内起始线；阅读方向与同级项相反的项从对侧边缘开始，如 FR6 所要求。这些项下嵌套的列表以各自项的行作为锚点；编号列表的内缩遵循 FR11。任务列表项、围栏代码、表格和分隔线渲染为对应结构，绝不渲染为字面源文本。围栏代码在每个界面上对长行换行；代码行绝不横向滚动或裁切（DEC-9）。
- **FR6 — 方向跟随承载它的文本。** 散文块——段落、标题、引用或列表项——在每个界面上按其自身文本的方向布局，包括 `Markdown`、`RichTextEditor` 和 `RichTextView`，任意嵌套深度皆如此。文本中没有强方向字符的块采用周围 Internationalization provider 的方向，这涵盖空块、数字、标点和图片。

  包含多个块的散文块——引用，或含多个段落的列表项——取其下所有文本中第一个强方向字符的方向，其内部每个块也按同样方式取自身方向。

  容器不是散文，无论包含什么，都采用父级方向：顶层取 provider 的方向，嵌套时取外层项的方向。列表据此排列标记和内缩，表格据此排列列，围栏代码块据此框定各行，每行再按该行第一个强方向字符取自身方向。

  表格单元格是容器，随表格排列，单元格文本在每个界面上按自身方向阅读。界面若将该文本包在块中，由块承载方向；若不包，由单元格承载，因此同一单元格在三个界面上阅读方向相同。

  方向决定块的对齐、逻辑内缩和光标移动方向。若界面从 provider 取这些，而块文本方向相反，右到左段落的光标会落在错误边缘，并随方向键反向移动。

- **FR7 — 语义相同。** 粗体、强调、删除线、行内代码和链接在每个界面上暴露相同的元素语义。链接的目标绝不包含其标题；标题作为链接的 title 暴露。文本中的命名和数字字符引用，如 `&copy;` 和 `&#169;`，在每个界面上渲染为其指代的字符；在行内代码和围栏代码中保持字面。每个界面都用 `Markdown` 导出的唯一解码器解码（DEC-5）。
- **FR8 — 代码块框架相同。** 围栏代码块显示相同的框架——其头部，或无头部时的角标组，语言标签和复制操作按 `component:CodeBlock` FR3 和 FR11 放置——在阅读和编辑模式下高度相同，切换不移动代码。编辑模式下框架——头部或角标组——位于可编辑文本之外：不属于文档，不可编辑。
- **FR9 — 原地阅读与编辑。** 编辑模式可增加光标、选区、占位符、焦点环、字段边框和内缩，以及工具栏。这些合计使整篇文档偏移一个常量：偏移后，每个块的顶部和高度与阅读模式相差不超过 2 px，每个段落保持行数不变。工具栏要么覆盖内容，要么占用阅读模式也预留的空间，使偏移在编辑期间不变。
- **FR10 — 滚动位置在切换后保留。** 阅读与编辑切换前位于视图顶部的块，切换后仍在视图顶部，误差在 FR9 偏移内。
- **FR11 — 编号列表缩进在列表内共享。** 编号列表可将标记空间从常规主题列表内缩加宽，以容纳该列表最宽的渲染计数器。阅读方向相同的同级项从同一条行内起始线开始文本；单个计数器不得移动其项的文本或其下嵌套的列表。计数器保持整行完整，不裁切、不截断、不与项文本重叠。同深度的不同列表在最宽计数器不同时可有不同内缩；每个嵌套列表从父项文本起点解析自身内缩。此许可不改变源嵌套，也不改变 DEC-6 的编号和标记样式。它不豁免渲染器一致性：对同一列表、主题、密度和可用行宽，Markdown 与 RichText 界面保持一致的文本起点和嵌套内缩，FR9 的阅读/编辑几何和重排要求仍然成立。

### 平台支持

- 支持的 feature/engine 下限：仓库的浏览器支持矩阵。
- 不支持的行为：界面尚不能渲染为结构的内容，渲染为其字面源文本。绝不丢弃。
- 浏览器证据：共享一致性 fixture 在手机和桌面宽度、浅色和深色、从左到右和从右到左下的真实浏览器块几何，以及一份长文档在中间位置切换阅读与编辑。

## 当前状态影响

`Markdown` 已为其自身输出渲染 FR2–FR4，以及除对侧边缘条款外的 FR5，但 FR7 指出的链接标题和 FR7 指出的字符引用除外。`RichTextEditor` 和 `RichTextView` 对其渲染的结构受 FR2–FR11 约束；其默认编辑器主题遵循 FR2 和 FR3。实现差距：`Markdown` 和 RichText 按 provider 的方向布局每个块（FR6，以及 FR5 的对侧边缘条款）；RichText 在 `editorTheme.ts` 中的 `direction: inherit` 覆盖是此差距的一部分。围栏代码行在两个界面上都取框架方向，因此两者都尚未满足 FR6 的逐行规则。`component:CodeBlock` 保持代码块方向不变（FR9），并将行内排序交给平台文本引擎，因此填补此差距会同时改变该记录和这些界面。`@astryxdesign/core/Markdown/parser` 和 `@astryxdesign/core/Markdown` 导出 `decodeMarkdownCharacterReferences`，即 RichText 界面导入的 DEC-5 解码器。`Markdown` 在每一层绘制圆点和十进制标记，RichText 将第二层项目符号绘制为圆点；两者都采用 DEC-6 的标记循环。RichText 采用 DEC-8：其包入口停止导出 `sharedEditorTheme`、`URL_MATCHER`、`EMAIL_MATCHER` 和 `Transformer`；`RichTextEditorToolbar` 增加 `BaseProps` 和 `ref`，并将 `linkOpensInNewTab` 重命名为 `hasNewTabLinks`；其 Lexical peer 范围移至 Lexical 0.52 minor。`Markdown` 渲染围栏代码时不换行、横向滚动，将采用 FR5 的换行；RichText 已对围栏代码换行。RichText 的编辑界面在每个宽度下都比阅读界面窄 18px，即字段内缩，因此接近可用宽度换行的行在编辑模式下可能比阅读模式多一行，违反 FR9；在手机宽度下，长围栏代码行确实如此。`Markdown` 通过 `component:CodeBlock`，以及 RichText 界面，将 Copy 浮在未指定语言的围栏代码上；两者都采用 `component:CodeBlock` FR11 放置的 FR8 角标组。RichText 代码块用 `component:CodeBlock` 的分词器着色，`RichTextEditor` 和 `RichTextView` 接受与 `Markdown`（`component:Markdown` FR30）相同的 `component:CodeBlock` 语言模块（FR13）的 `codeLanguages` 列表，用值的 `name`（逐字显示的标识符，`component:CodeBlock` FR13）标记匹配的围栏，与 `Markdown` 一致，因此阅读和编辑绘制并标记相同的语言，但首个词超出字母、数字和下划线的围栏除外，如 `c++`、`c#`、`objective-c`、`rust,ignore` 或 `diff-ts`：`Markdown` 按前导词字符读取围栏（`component:Markdown` FR29），而 RichText 保留整个首个词。

## 决策日志

### DEC-1 — 一致性是共享契约，而非复制 `Markdown`

**引用：** `spec:AST-061/DEC-1`
**决策者：** cixzhang，2026-10-06

读者在同一文档的阅读和编辑界面之间切换，因此文档在两者上必须外观和含义一致。契约是 CommonMark 语义加共享令牌，因为读者的预期来自这些。当 `Markdown` 是偏离它们的一侧时，`Markdown` 改变。
拒绝：将当前 `Markdown` 输出作为基准，因为这会将其缺陷复制到每个编辑器界面。

### DEC-2 — 编辑控件使文档偏移，但绝不重排

**引用：** `spec:AST-061/DEC-2`
**决策者：** cixzhang，2026-10-06

编辑器需要光标、工具栏和字段框架，因此编辑模式无法与阅读模式像素级相同。常量偏移保持读者的位置：每行相对其他行的位置不变，滚动锚点留在视图顶部。2 px 吸收渲染器间的亚像素舍入；不允许不同的间距值。

### DEC-3 — 字符引用渲染为解码后字符

**引用：** `spec:AST-061/DEC-3`
**决策者：** cixzhang，2026-10-06

读者在一个界面上看到 `&copy;`、在另一个上看到 `©`，就是在看两份文档。CommonMark 将引用渲染为其指代的字符，因此两个界面都如此；代码显示所键入的确切内容。

### DEC-4 — 阅读和编辑共享代码块头部

**引用：** `spec:AST-061/DEC-4`
**决策者：** cixzhang，2026-10-06

语言标签在两种模式下都告诉读者代码是什么，仅出现在一种模式下的头部会在切换时移动每一行代码。头部是文档周围的框架，不是文档内容，因此编辑永远触及不到它。

### DEC-5 — 字符引用的唯一解码器

**引用：** `spec:AST-061/DEC-5`
**决策者：** cixzhang，2026-10-06

`decodeMarkdownCharacterReferences(text)` 从服务端安全的 `@astryxdesign/core/Markdown/parser` 子路径和 `@astryxdesign/core/Markdown` 导出，返回将每个有效命名或
