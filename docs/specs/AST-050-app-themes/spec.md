# 应用主题系统规范

## 意图

构建者（无论是人还是编码代理）想要一个使用一个或多个主题的应用：第一方主题、来自已安装集成包的主题，或应用自己创建的主题。他们想要找到主题、添加主题、选择默认主题、让用户在运行时切换主题，并确认配置正确。

应用以源码形式复制的主题会停止接收其所有者的更新，失去包身份，并且必须由应用重新构建。它还会失去其包随之加载的任何样式表（例如字体），因此可能以回退字体渲染且不报错。使用多个主题的应用需要一个地方列出它们、一种在它们之间切换的方式，以及一个证明配置正确的检查。

本记录规定应用如何通过 CLI 查找、声明、导入、切换和检查其主题。规则对每个主题都相同：应用通过导入主题的构建形式并将其传递给 `Theme` 来使用主题，并通过扩展该主题来自定义它。复制主题源码是显式的作者 Fork。`theme add` 通过两个生命周期阶段达成该规则（FR12）：一个可选的导入与其已弃用的复制默认值并存，导入在所有者安排的次要版本中成为默认值。`architecture:theme-application` 已支持在一个页面上使用多个构建主题，因为构建主题的 CSS 作用域限定在主题名称下，切换只改变活动身份。`spec:AST-017` 规定兼容性、生命周期和响应字段，`spec:AST-042` 规定命令准入，`spec:AST-040` 规定对消费者文件的写入，`architecture:cli-surface` INV19 和 INV24 规定集成项的描述方式。

## 非目标

- 用于切换主题和保存用户选择的 Core 组件。生成的模块为应用提供了切换器所需的一切；Core 组件是单独的组件决策。
- 延迟加载主题样式表。
- 查找未安装的主题。
- 改变主题的编写、编译或运行时应用方式。
- 合并或重命名第一方主题包。
- 使主题源码归 CLI 所有。生成的模块只导入并列出应用的主题；每个主题的源码仍归其作者所有。
- 字体样式表如何交付字体。包中的字体文件和字体服务都满足 FR7；由包选择。
- 读取 0.6 主题目录（`themes/manifest.json`）。包使用类型化描述符描述主题，没有根目录持有目录文件（`architecture:cli-surface` INV24），也没有主题命令读取它。
- 满足本契约的等效内部实现仍然有效。生成模块的确切文本、发现代码和回执字段顺序属于实现。

## 需求

- **FR1 — 导入主题会将其添加到应用。**
  `theme add <slug> --import [--package <package>]` 必须通过将主题添加到应用的主题记录（FR3）并重新生成应用的主题模块（FR2），使主题成为应用的一部分。它不得将主题源码复制到项目中，也不得编辑应用代码。导入已添加的主题会重新生成模块并报告无变化。导入已从不同所有者添加的 slug 会将其切换到新所有者并报告该变化。`--import` 与目标路径或 `--overwrite`（属于复制，FR12）一起使用时，必须在写入前失败。
- **FR2 — 一个生成的模块。** CLI 必须维护一个模块，导入每个已添加主题的构建模块和样式表。它导出 `themes`（每个已添加主题以其 slug 为键）和 `defaultThemeSlug`（默认 slug）；TypeScript 模块还导出类型 `ThemeSlug`，即已添加 slug 的联合类型。这些导出是模块的公共契约，其主题记录（FR3）不属于其中。模块带有生成标记，CLI 重新生成整个模块而不是编辑它（`spec:AST-040/FR5`）。项目使用 TypeScript 时模块为 TypeScript，否则为 JavaScript。它有一个固定位置：项目有 `src` 文件夹时为 `src` 文件夹中的 `astryx-themes.ts` 或 `astryx-themes.js`，否则为项目根目录。已存在的模块保持原位，即使项目获得或失去 `src` 文件夹。没有配置选择位置（`spec:AST-017/FR19`）。当该位置存放了 CLI 未生成的文件，或存在多个生成的模块时，命令必须在写入前失败并指出这些文件。
- **FR3 — 模块是应用的主题记录。** 主题模块以 CLI 无需运行模块即可读取的形式记录每个已添加主题的 slug 和所有者（包名或项目的本地主题根目录）以及默认 slug。导入型 `theme add`、`theme remove` 和 `theme use` 读取该记录、修改它并重新生成模块。默认值必须是已添加主题之一。没有 `package.json` 字段、配置键或环境变量记录或选择应用的主题（`spec:AST-017/FR14`、`spec:AST-017/FR19`）。在有主题模块的项目中，读取应用默认主题的命令读取模块的记录；在没有主题模块的项目中，现有的 `astryx.theme` 字段保持其已发布含义。CLI 不读取 `ASTRYX_THEME`（DEC-7）。
- **FR4 — 集合和默认值由命令管理。**
  `theme remove <slug>` 从应用中移除主题，`theme use <slug>` 使已添加主题成为默认。移除默认主题必须失败并指出 `theme use`；对未添加的主题使用 `theme use` 必须失败并指出导入命令。每个命令都重新生成模块（FR2）。
- **FR5 — 一个回执描述应用的主题。** 导入型 `theme add`、`theme remove` 和 `theme use` 必须返回 `theme.app` 响应：每个已添加主题及其 slug、所有者、导入的模块和样式表；默认 slug；模块路径；以及命令所做的更改。文本输出显示相同事实。项目中的首次导入还显示一次性接线：从模块导入 `themes` 和 `defaultThemeSlug`，并将 `themes[defaultThemeSlug]` 传递给 `Theme`。
- **FR6 — 弹出是作者 Fork。**
  `theme eject <slug> [path] [--overwrite] [--package <package>]` 必须像复制型 `theme add`（FR12）一样将主题的完整源码目录精确复制到项目中，具有相同的路径安全、覆盖规则和回滚。它还必须复制主题的同名描述符（`architecture:cli-surface` INV24），使弹出的主题成为可发现的本地主题（FR8）。副本不得声称由主题的原始所有者维护。它返回 `theme.add` 响应的复制字段作为 `theme.eject` 响应，描述符在其文件列表中。
- **FR7 — 包将每个主题暴露以供导入。** 包通过在 `./themes/<slug>` 导出构建模块并在 `./themes/<slug>.css` 导出样式表，使主题可导入。恰好拥有一个主题的包可以改为导出 `./built` 和 `./theme.css`。当主题需要非系统字体时，包应导出字体样式表至 `./themes/<slug>.fonts.css`，单主题时为 `./fonts.css`。字体样式表负责加载其字体：它可以通过 `@font-face` 规则附带字体文件，或从字体服务导入。当主题没有可解析的构建模块和样式表时，导入必须失败并指出缺失内容；它绝不回退到复制或运行时源码。`integration add theme` 必须写入这些导出，`integration verify` 必须在导出的主题模块、样式表或字体样式表无法从打包的 tarball 解析时失败，或在主题同时导出构建模块和样式表且任一与其源码不匹配时失败。导出的模块在以下情况与其源码匹配：它是 `theme build` 从该源码写入的模块，或它只加载主题自身的样式（DEC-10）：其每条语句都为主题导出的样式表或字体样式表导入副作用，除了一条语句，该语句从 `theme build` 写入的模块重新导出全部或仅其主题，使用主题的导出名。只导出该对中一部分或完全不导出的主题，在导出的每个路径都可解析时仍可打包，`integration verify` 会警告缺失或不匹配的内容。
- **FR8 — 本地主题像包主题一样添加。** 项目的本地主题根目录是 `src/themes`：复制型 `theme add` 写入的文件夹，也是 `theme eject` 默认复制到的文件夹，在没有 `src` 文件夹的项目中也是如此。该处的主题目录（与集成主题形状相同，`architecture:cli-surface` INV19）像包主题一样被列出和导入。其构建模块和样式表是 `theme build` 在其源码旁写入的文件，其字体样式表（如有）是旁边的 `<slug>.fonts.css`。当构建模块或样式表缺失时，导入必须失败并指出构建命令。当本地主题和包主题共享 slug 时，导入会添加本地主题，除非 `--package` 指定了包，`theme list` 会显示两者及其所有者。复制型 `theme add` 仅解析捆绑主题和包主题，与已发布版本一致。
- **FR9 — 模块只导入构建主题。** 生成的模块必须导入构建主题、其样式表及其字体样式表（当包导出时），绝不导入主题源码用于运行时样式注入，因此每个已添加主题在首次绘制时即存在，切换从不等待样式。
- **FR10 — 列表显示应用的主题。** `theme list` 必须为项目标记每个主题是否已添加、是否为默认，并指明它是捆绑的、来自包还是本地的。这些字段是增量的，本地主题作为额外条目加入列表。
- **FR11 — Doctor 证明配置正确。** 在有主题模块的项目中，doctor 必须检查，且仅在正面证据下通过每项检查：
  1. 每个已添加主题的所有者已安装，其模块和样式表可从项目解析；
  2. 主题模块存在，带有 CLI 的生成标记，且与 CLI 从其携带的记录生成的内容完全一致；
  3. 项目源码导入主题模块（无法证明时警告）；
  4. 没有构建主题模块在未导入其样式表的情况下被导入；
  5. 每个已添加的本地主题已构建，其输出与源码匹配；
  6. 没有已添加主题直接设置私有 `--_*` 变量（`architecture:theme-compilation` INV6）；
  7. 每个已添加主题的 `@astryxdesign/core` peer 范围接受已安装的 Core；
  8. 默认主题是已添加主题之一；
  9. 已添加主题命名的每个字体族是系统字体或由模块导入的字体样式表加载（无法证明时警告并指出字体族，例如样式表从字体服务导入字体时）；
  10. 没有两个已添加主题为同一选择器在其自身主题作用域外写入不同规则，因为所有已添加样式表同时加载。

  每个失败都指出修复它的确切命令。

- **FR12 — 复制默认值走完其生命周期。** 复制型 `theme add`、其选项及其 `theme.add` 响应是已发布契约。`theme add` 通过其 `spec:AST-017` 生命周期达成 FR1：
  1. **复制默认值已弃用。** 不带 `--import` 时，`theme add <slug> [path] [--overwrite] [--package <package>]` 复制主题源码并返回已发布的 `theme.add`。每次调用最多发出一次 stderr 警告，为 Fork 指出 `theme eject`，为使用主题指出 `theme add --import`，其机器结果携带弃用 ID 和替代方案（`spec:AST-017/FR28`、`spec:AST-017/FR29`）。其退出状态、规范输出和机器结果的其余部分是已发布的。`theme add --list` 在每个阶段保持其机器结果，其文本指出当前阶段的命令。
  2. **清理在声明的次要版本中落地。** 当 `main` 声明次要版本时，描述该更改的 `[breaking]` Changeset（`spec:AST-017/FR31`）使 `theme add <slug>` 按 FR1 所述导入，无论是否带 `--import`，并返回 `theme.app`，且 `theme add` 不接受目标路径或 `--overwrite`，它们保留在 `theme eject` 上。该次要版本不携带本记录的其他增量（`spec:AST-017/FR39`）。

  现有项目按如下方式迁移（`spec:AST-017/FR8`）：
  1. 使用 `theme add` 复制的脚本运行带相同参数的 `theme eject`；希望应用使用主题的脚本运行 `theme add --import`，其在清理后保持含义。没有 codemod 重写这些调用，因为正确的替代取决于调用者的意图；弃用警告指出两者。
  2. 由 `theme add` 复制的主题是应用源码。CLI 不得移动、更改或删除它，应用对它的导入继续工作。副本缺少主题的描述符，因此 `astryx upgrade` 必须提供一个项目 codemod，在本地主题根目录中每个此类副本旁写入缺失的描述符，标记为未维护，使副本成为本地主题（FR8）。codemod 不更改其他内容，第二次运行不更改任何内容（`spec:AST-040`）。
  3. 在该 codemod 运行之前，本地主题根目录中存放无描述符主题源码的文件夹不得使主题命令或 doctor 失败。`theme list` 和 doctor 将其命名为未迁移副本，并指出升级命令，它不作为主题列出或导入。仅对本地主题根目录，这取代了此类文件夹使发现失败的规则（`architecture:cli-surface` INV19）。
  4. 没有主题模块的项目保持原样工作。Doctor 报告 CLI 不管理其任何主题并指出导入命令；FR11 检查在主题模块存在后适用。
  5. 设置 `ASTRYX_THEME` 的调用者使用 `theme use` 选择默认值，或在没有主题模块的项目中使用 `astryx.theme`。

- **FR13 — 每个面向构建者的界面一致。** 主题指南、集成指南、生成的代理文档和 `init` 的后续步骤必须描述相同的工作流：导入主题、一次性接线模块、通过导出的主题切换、扩展主题以自定义它、仅在 Fork 时弹出。它们在复制默认值弃用期间指出 `theme add --import`，在移除后指出 `theme add`。没有界面教导复制作为使用主题的方式。
- **FR14 — 搜索找到列表显示的主题。** `astryx search` 必须将 `theme list` 显示的每个主题索引为 `theme` 结果，`--type theme` 选择它。主题结果必须携带其 slug 作为 `name`、显示名称、描述、提供它的包，以及 CLI 的 FR12 阶段的 `theme add` 命令：没有 `--import` 的 CLI 中为 `theme add <slug>`，复制默认值弃用期间为 `theme add --import <slug>`，清理后为 `theme add <slug>`（FR13）。主题的 slug 和显示名称是其名称，其描述是散文（DEC-9）：主题仅通过描述共享的查询词将其排名为描述提及，绝不作为名称或关键词匹配，因此该词单独绝不会将主题排在按名称、标题或关键词匹配它的结果之上。搜索主题不得需要 `@astryxdesign/core`，因为列出它们不需要，所以应用外的开放搜索包含它们（DEC-8）。帮助、清单和 API 参考必须列出 `theme` 域及其结果字段。

### 平台支持

- 支持下限：CLI 支持的每个运行时和包管理器，以及从 JavaScript 模块导入 CSS 的每个工具链。
- 不支持的行为：无法从模块导入 CSS 的工具链自行加载每个已添加主题的样式表；模块仍导出主题，doctor 检查 4 指出要加载的样式表。
- 浏览器证据：为生产构建的消费者应用导入第一方、集成和本地主题，在首次绘制时渲染默认主题，并在三者之间切换。

## 当前状态影响

- `theme add` 获得 `--import`；其复制默认值和 `theme.add` 响应已弃用，并在计划的次要版本中离开 `theme add`（FR12）；`theme eject`、`theme remove` 和 `theme use` 加入 `theme` 命令；`theme list` 获得其应用字段并列出本地主题；
- `astryx search` 找到 `theme list` 显示的主题，作为 `theme` 域，并将仅在主题描述中找到的词排名为散文（FR14）；
- `architecture:cli-surface` INV19：集成主题是可导入的包，可编辑源码是显式弹出；
- `integration add theme` 写入主题导出，`integration verify` 检查它们；
- doctor 的主题检查在有主题模块的项目中为 FR11，在没有主题模块的项目中为 FR12 报告；
- `astryx upgrade` 携带为副本提供描述符的 codemod（FR12）；
- CLI 停止读取 `ASTRYX_THEME`（DEC-7）；
- 主题指南、集成指南、代理文档和 `init` 后续步骤描述 FR13 工作流。

`architecture:theme-application` 和 `architecture:theme-compilation` 不变。

## 验证

| 契约 | 验证 | 代表性状态 | 变更或失败预期 |
| -------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR1, FR2 | 主题命令测试和真实消费者 | 首次导入；重复导入；从另一所有者再次导入的 slug；模块的导出；`--import` 与目标路径或 `--overwrite`；模块位置的手写文件；无 TypeScript；无 `src` 文件夹；稍后添加 `src` | 源码被复制、应用代码更改、重复导入更改文件、第二所有者的导入保留旧所有者、`--import` 与复制选项写入任何内容、导出缺失或重命名、主题记录被导出、用户文件被替换或现有模块移动 |
| FR3,
