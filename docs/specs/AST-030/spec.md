## 意图

Pull Request 检查按变更可能影响的仓库表面来路由，而不是按一份不断扩大的"变更看起来不影响的工作"清单来路由。贡献者应获得能观察其变更的检查，而一个狭窄的运维类 Node 工具变更不应等待无关的组件、浏览器、Storybook 或应用构建。

分类器产出一组被触及的表面。只有当每个变更路径都依据可信的基线分支策略完成分类，且所选检查覆盖该集合中的每个表面时，通道才可以跳过工作。混合、不完整或未知的范围使用宽通道。

**通道**（lane）是某个表面上一个独立路由的逻辑测试或构建归属方。一个通道可以派发多个工作流作业或步骤，也可以汇入一个历史必需检查的汇合。作业、工作流、必需上下文和投影状态是执行或报告机制——不会仅因名称不同就成为额外的通道。

## 非目标

- 在一次变更中重写每个 CI 作业，或为每个包专门化通道。
- 为已由现有表面拥有的工作新增测试专用或构建专用通道。
- 将变更表面路由应用于合并后的 `main` CI。
- 定义兼容性语义或发布对增量类别。这些属于 [`spec:AST-017`](../AST-017/spec.md)；本记录只路由它们的检查，并拥有精确 main 发布检查的执行边界。
- 移除必需检查名称（除从其中去掉 `spec-owner-approval` 外，FR15），或移除分支保护、合并队列覆盖、规范内容的归属方批准。
- 从文件扩展名、目录名或"不存在已知风险路径"推断安全性。
- 将测试、规范、生成文件或 changeset 视为其旁的公开或运维表面未被触及的证据。

## 需求

- **FR1 — 分类是正向的、基于集合的。** 每个变更路径必须映射到一个或多个具名表面。通道选择必须使用这些表面的并集，而不是对无关路径的排除谓词。没有精确规则的路径必须加入 `shared-or-unknown`。
- **FR2 — 分类法遵循检查归属。** 分类器只能命名具有具体检查归属方和依赖边界的表面。初始分类法及当前归属方如下：

  | 表面                | 正向路径归属                                                                                                                       | 当前检查归属方                                                                                                                                                   |
  | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `knowledge`         | 规范的系统、家族、设计、主题、组件和模块记录                                                                                       | 知识校验、当前规范内容的规范归属方批准，以及直接或通过其导入的模块读取变更记录的 Vitest 测试                                                                     |
  | `docsite`           | docsite 应用                                                                                                                       | docsite 生成和测试                                                                                                                                               |
  | `node-tooling`      | 已准入的运维 Node 工具，其消费者由 Node 契约测试覆盖                                                                               | Node Vitest、仓库护栏和 ESLint                                                                                                                                   |
  | `runtime:<package>` | Core、Lab、Charts、Rich Text、Vega、CLI 和 Build 的公开源码和包契约                                                                 | 该包的单元/类型检查，加上当前宽构建和下游消费者检查；Build 的归属方包括生产 CSS 层浏览器行为                                                                     |
  | `theme-build`       | 已发布主题包和主题编译产物                                                                                                         | 主题测试、主题包构建、主题家族浏览器行为，以及适用时的稳定视觉证据                                                                                               |
  | `storybook-visual`  | Storybook 故事/配置，以及视觉、无障碍或 RTL 审计基础设施                                                                           | Storybook 构建、预览/视觉报告发布，以及适用的浏览器、视觉、无障碍和 RTL 检查                                                                                     |
  | `shared-or-unknown` | 共享配置、依赖图、工作流、分类器、生成归属、歧义路径，以及每个未分类路径                                                           | 所有适用的 Pull Request CI 检查                                                                                                                                  |

  一个类别不会仅因存在于本表中就获得专门化通道。在所选每个表面都有已准入、完整的专门化归属方路由之前，该表面集合使用宽检查集。`shared-or-unknown` 始终使用宽检查集，但 Changeset 或 Lab-only 变更旁携带的 Lab 组件入口文件除外，后者保留 Lab-only 路由（FR26）。

- **FR3 — 分类使用可信基线策略。** Pull Request 代码不得选择自己的通道。工作流必须从可信基线 ref 加载分类器及每个分类器依赖，然后将该策略应用于合并基三点击路径集。对于 Lab 组件的入口文件（FR26），可信分类器还读取 GitHub 对这三个文件的补丁文本。它将文本作为数据读取，逐行匹配固定模式且从不执行，因此 Pull Request 只提供基线策略所判断的数据，绝不提供策略本身。工作流变更使用宽通道，除非它们是已准入工具的非 PR 派发工作流。分类器、分类器依赖和路由测试的变更使用宽通道。
- **FR4 — 不确定性故障关闭。** 缺少合并基、缺少可信分类器依赖、分类器失败、文件列表为空或不完整、歧义重命名、未知路径，或没有可信 PR 路径集的合并组事件，必须选择宽通道。任何回退都不得授予专门化通道。
- **FR5 — 混合范围保留每个归属方。** 触及多个已分类表面的变更必须运行其检查的并集。它不得为未触及的表面运行专门化通道。包含 `shared-or-unknown` 的集合（除 Changeset 或 Lab-only 变更旁携带的 Lab 组件入口文件外，FR26）、来自 FR3–FR4 的故障关闭条件，或任何没有完整已准入专门化归属方路由的所选表面，必须使用宽 CI。运行时码旁的规范不会隐藏运行时表面。
- **FR6 — Node 工具准入是显式的。** 只有当依赖分析证明包运行时、组件 UI、主题/构建输出、Storybook/视觉证据和浏览器行为未被直接改变，且每个运维消费者都有 Node 契约测试时，Node 程序才能进入 `node-tooling`。仅允许对专用于非发布工具的目录进行目录级准入；其他目录级或扩展级准入被禁止。
- **FR7 — 必需检查名称保持稳定。** `test`、`build`、`docsite-test` 和 `lint` 必须继续通过其现有作业或汇合作业在每个 Pull Request 上报告。专门化通道在那些作业内跳过其拥有的步骤；它不移除历史必需上下文。任何拥有的通道失败必须使其汇合失败。必需 lint 不比较 main 的包声明与最新稳定发布；AST-017 将预发布排序分配给 canary 发布者，并将不可变发布合并回验证保留在必需 lint 中。
- **FR8 — 初始工具准入。** `node-tooling` 覆盖 `scripts/score-ledger.mjs`、`scripts/score-ledger.test.mjs`、`internal/scripts/` 和 `.github/workflows/crowdin-upload.yml`。它运行 Node 项目和必需 lint 工作流，包括仓库护栏。它跳过 UI Vitest 项目、组件分析、docsite 生成、生产包、Storybook 和 Sandbox 构建、预览/视觉报告发布，以及浏览器/主题/视觉/a11y/RTL 作业。可信 post-CI 工作流必须明确报告视觉检查不适用，并移除过时预览链接而不入队预览发布者。Sandbox score-ledger 投影必须为其消费的导出提供 Node 契约测试，才能启用此通道。
- **FR9 — 路由测试对变异敏感。** 测试必须证明预期的快速路径和不安全的近似失误。至少覆盖纯工具；纯规范；组件规范加组件代码；模块规范加 Table 插件代码；工具加组件代码；工作流或分类器自变更；未知路径；共享基础设施；重命名历史；不完整输入；以及每个含组件包中的公开源码。移除任何故障关闭边界必须使测试失败。
- **FR10 — 新表面遵循一个准入约定。** 新表面必须在实现前通过归属方批准的修正案准入本记录。修正案必须命名其正向路径归属、依赖边界、测试命令、一个独立路由的测试归属方、构建命令和适用时一个独立路由的构建归属方、混合范围行为、必需检查投影，以及变异敏感的路由测试。新的套件、功能、组件、主题家族或测试类型本身不是新表面。
- **FR11 — 每个表面拥有一个测试通道和适用的构建通道。** 一个表面可以定义多个测试或构建命令、作业或步骤，但恰好一个独立路由的测试通道，以及适用时一个独立路由的构建通道，必须拥有它们。现有表面内的新覆盖必须加入这些归属方，且不得创建单独路由的通道或必需上下文。现有历史汇合保持稳定。默认的触及组件检查（FR12）是视觉、无障碍和 RTL 归属方对变更所触及组件的 Pull Request 覆盖：其视觉部分在 `pr-visual` 内运行，其无障碍和 RTL 部分在旁的一个咨询作业中运行，不报告必需上下文。触及组件的浏览器无障碍契约（FR12）在其自己的并行作业中运行，不报告自己的必需上下文：现有 `test` 汇合等待它并随其失败（FR7），因此 `test` 保持为唯一必需名称，且不路由任何新表面通道。所选表面的专用归属方尚未准入时，继续通过宽 CI。Build 包的测试归属方包括其生产 CSS 层级联行为。主题家族编译保持为 `theme-build`，不会仅因两者都涉及 CSS 就成为 Build。
- **FR12 — 视觉回归有一个共享的 Pull Request 工作流。** 每个表面的每个视觉回归测试必须使用现有 Storybook 框架和 `.github/workflows/ci.yml` 中的单一共享归属方（`pr-visual`）。该工作流可以使用多个作业、步骤和构建产物，但视觉捕获和回归比较不得在另一个工作流中运行，包括计划、post-CI、合并后或手动替代归属方。规范运行的报告发布不是另一个测试归属方：它必须消费该运行的构建产物，而不重新捕获或重新比较像素。显式全计划基线捕获必须保留在 `ci.yml` 中；它是维护操作，不是发布门禁。经审查的基线更新必须消费该捕获，通过正常 Pull Request 更新版本化仓库基线，并与自动合并或发布工作保持分离。GitHub Pages 不得作为基线或报告存储。
  发布证据必须来自同一工作流中显式的 `operation=release-check` `workflow_dispatch`，从 `main` 派发并绑定到其精确事件 SHA。它必须以全范围运行规范 `pr-visual`（**稳定视觉回归**）、`pr-a11y` 和 `pr-rtl` 归属方：封闭的稳定视觉计划和未过滤的无障碍/RTL 组件名册。变更文件、聚焦、冒烟和 no-op 路径不得缩小发布检查。在 Pull Request 上，视觉（`visual-scout`、`pr-visual`）、无障碍（`pr-a11y` 及其守卫和规范）和 RTL（`pr-rtl` 及其分支）归属方必须各自在事件时仅当 Pull Request 携带该套件标签时以其选择加入的范围运行（FR13）：`ci:run-visual`、`ci:run-a11y` 或 `ci:run-rtl`，每种情况下最后应用者须具有 write、maintain 或 admin 访问权限，且无法确认的查找不运行任何内容。标签只运行其自己的套件。Lab-only Pull Request（FR26）不运行默认触及组件检查，也不运行契约作业；其标签仍运行其套件。没有标签时，Pull Request 更新不以其选择加入的范围运行这些归属方中的任何一个，且没有必需上下文依赖它们；它改为运行一个默认触及组件检查：仅对变更所触及组件的视觉、无障碍和 RTL，绝不涉及其反向依赖方，针对 Pull Request 的 Storybook 构建，并在 15 分钟预算内。其视觉部分是 `pr-visual` 的默认模式，即对触及 Core 组件的聚焦检查，绝不升级到发布计划，因此 `pr-visual` 保持为唯一视觉归属方；其无障碍和 RTL 部分以及每组件记录是 `pr-touched-components`，在一个标准 runner 上。宽变更跳过它：触及超过五个组件，或更改共享样式（主题、token，或包共享 `theme`、`utils`、`hooks`、`internal` 或 `Layer` 文件夹中的 `.stylex.ts` 文件）；仅行为共享代码不是宽变更。每个变更，包括宽变更，还会对其添加或更改且 Pull Request 中无其他审计覆盖的每个故事文件进行无障碍审计，仅新违规。没有任何东西自行启动完整套件；宽变更的检查是标签后的完整套件。没有必需上下文依赖触及检查，它记录每个触及组件按套件的通过、失败、变更或未运行结果，或记录变更为宽变更及其触及组件数，用于 Pull Request 评论。在默认检查旁，一个契约作业在 Chromium 中运行变更所触及组件的浏览器无障碍契约。它只需要 Pull Request 的 Storybook 构建。首先它按路径顺序运行变更添加或修改的浏览器无障碍规范文件，最多四个，由从合并提交读取的各自 `@pr-a11y` 行路由；变更的 `audit` 规范等待其组件审计 Pull Request。然后，包括宽变更，它按路径顺序运行每个触及组件拥有的 `scoped` 和 `release-only` 规范文件，由带标签运行使用的同一 `@pr-a11y` 范围和规范位置映射找到。然后，在剩余时间内且最多一分钟，它按最近优先运行通过源值导入渲染触及组件的组件文件夹的 `scoped` 和 `release-only` 规范文件。它不运行未变更的 `audit` 或 `always` 规范。契约作业与单元测试作业并行运行，且不得成为 Pull Request 的关键路径：它在 Storybook 构建后启动，必须在最慢单元测试作业前完成，因此直到必需 `test` 汇合报告的时间不增长。它在八分钟后停止并计划其中六分钟：仅当文件的记录持续时间适合这六分钟的剩余部分时才启动该文件，因此比计划慢三分之一的 runner 仍能完成其启动的每个文件。无法在预算内完成的契约文件报告为未运行，不拆分。它未运行的每个文件，因该预算或四文件限制，在检查的摘要和注释中报告为未运行，并附运行它的标签。启动但未完成的规范失败。失败的契约使必需 `test` 汇合失败（FR7）并阻止合并。未运行的文件通过汇合，因此跳过绝不读作通过，溢出绝不读作失败。选择加入的 PR 的 a11y 必须保持范围为变更组件加快速交互守卫，并且还运行变更组件直接拥有的 `release-only` 规范文件，绝不通过共享范围 token 或未知范围；完整 a11y 扫描、全仓库规范测试契约及其证据上传必须仅在此工作流中为 `release-check` 运行。缺失、失败、取消或跳过的必需工作必须阻止 release-check 汇合。请求和汇合必须验证被检查的 SHA 是派发事件 SHA，并在运行开始和完成时仍是当前远程 `main` 的祖先。发布调用方必须在创建发布分支前立即获取并重新检查同一祖先关系。`main` 后来的快进移动不使该回执失效：发布必须从精确被检查的 SHA 切出，后续提交保持为下一发布输入。从当前 `main` 历史中移除被检查 SHA 的重写或分叉使回执失效。这取代仅组成 PR 的发布门禁，而非规范检查的现有发现策略。Main 的重通道工作流必须为 `main` 的 tip 派发该 release-check，绑定到该提交，在推送到 `main` 时和每刻钟计划时，除非 tip 已有一个或最近 175 分钟内已派发一个，因此三小时后的刻钟滴答会派发（DEC-11，FR24）。等待时被替换且从未运行的检查不计入。一个检查覆盖直到其提交的每个合并，因此每个合并由下一个覆盖。派发的检查共享一个并发组，仅因发布重新检查而取消运行中的检查（FR23）：最多一个运行、一个等待。`main` 已越过的推送将其检查留给更新的推送。该 release-check 运行是 main 的结果，失败通过原子 Pull Request 前向修复。Main 自己的快速检查（类型检查、带每提交大小记录的包构建，以及导出同步）仍为每次推送运行；其完整单元套件按自己的计划约每小时运行，并与每个 release-check 一起运行，如 FR21 所述。发布检查不得捕获基线候选、发布基线，或使用单独的每日工作流或追溯接受状态。部署、无障碍、RTL 和 vibe 证据在其不重复视觉回归时可以保留其工作流和构建产物。新的或现有的表面、组件、包、主题家族或视觉套件必须加入规范工作流。仓库守卫必须拒绝独立的视觉归属方，同时保留合法的非视觉构建产物使用。
- **FR13 — Pull Request 上的宽 CI 运行变更所及。** 在 `pull_request` 事件上，若可信分类未发现共享基础设施，宽 CI 保留每个必需上下文和 FR12 路由到 Pull Request 的
