## 意图

为稳定的 Astryx Web 组件指定唯一负责方，统一管理浏览器支持、原生特性采用和降级回退。组件规范继承此共享基线，只记录明确的例外。

完整路径与回退路径都必须满足组件当前的无障碍契约及适用的 [WCAG 2.2 Level AA](https://www.w3.org/TR/WCAG22/) 要求。辅助技术的证据仍由其他规范单独负责。

## 非目标

- 在用户结果等价时，要求实现或像素完全一致。
- 为所有缺失的浏览器特性提供 polyfill。
- 取代 [AST-003](../AST-003/spec.md) 中针对层的契约，或 [AST-002](../AST-002/spec.md) 中的公共 API 准入规则。
- 在本规范 Pull Request 中实现生成的行、消费者文档更新、CI 或发布工具。

## 要求

- **FR1 — 单一滚动兼容模型。** 当前 Web Platform Baseline 为完整支持层级。Baseline 减两年为降级回退层级。低于该层级，Astryx 不作任何支持承诺。
- **FR2 — 兼容性行是生成的。** 浏览器/版本行由已批准的 Baseline 数据和权威浏览器发布数据生成；绝不作为手写的版本声明维护。生成的行位于公开的 [浏览器支持指南](../../../packages/cli/assets/docs/browser-support.doc.mjs)，并记录来源和刷新日期。TypeScript 目标、构建目标和特性表不作为支持证据。
- **FR3 — 始终包含明确的浏览器支持行。** 独立于生成的 Baseline 覆盖范围，Astryx 明确支持：
  - 桌面端最新稳定版 Chrome；
  - 最新稳定版 iOS 上的 Safari；以及
  - 对于触控呈现，最新稳定版 Android 上的 Chrome（`spec:AST-094`）。

  “最新”指从权威浏览器发布数据识别并刷新的当前稳定版，而非手写版本。其他浏览器可由生成的 Baseline 兼容性行代表；本决定不将桌面端 Safari 或 Firefox 列为额外的明确支持行。

- **FR4 — 兼容性、明确支持和测试覆盖保持区分。** 浏览器支持指南分别标注生成的 Baseline 兼容性、具名明确支持和当前测试覆盖。浏览器被纳入生成的兼容性或明确支持，并不意味着在该浏览器中有自动化通道或逐 Pull Request 的证明。
- **FR5 — 受支持浏览器获得完整的必需行为。** 完整支持层级中的每个浏览器以及每个具名明确支持行，都获得组件当前的行为、无障碍、状态、渲染器和交互契约。缺失原生特性不会静默收窄这些要求。
- **FR6 — 原生特性通过能力检测。** 组件检测其使用的 API 或 CSS 能力，而非根据浏览器名称推断。仅当存在可复现缺陷、回归测试夹具以及审查或移除条件时，才允许针对特定引擎的窄范围变通。
- **FR7 — 降级回退保留任务。** 在 Baseline 减两年层级中，组件要么提供等价行为，要么记录降级回退。回退只能省略具名增强，且必须保留主要任务、适用的无障碍要求、稳定状态与回调、清理以及重复使用。
- **FR8 — 降级回退不得损坏。** 它不得抛出异常、渲染无效或 `NaN` 几何、隐藏必要内容、使控件不可达、孤立或困住焦点、阻塞周围页面、破坏受控状态、卡在待处理状态，或闪现错误的打开、关闭、加载、定位或样式状态。
- **FR9 — SSR 与水合保持一致。** Core 组件具备 SSR 能力，除非其组件规范记录了 FR12 例外。客户端指令不能豁免组件，因为框架会在服务器上渲染客户端组件。具备 SSR 能力的组件在服务器渲染期间或在水合服务器标记的客户端渲染期间，不读取浏览器能力、几何、输入模态、绘制时机或用户代理状态。水合渲染产生的标记与服务器相同。水合后增强从可用状态开始，不引入不匹配、损坏的中间状态或可见的错误状态。
- **FR10 — 浏览器自有行为需要真实浏览器证据。** 源码、单元和 jsdom 测试可以证明防护和确定性状态。对布局、绘制、焦点、原生 Popover 或 Dialog 行为、顶层顺序、浏览器事件时机或水合呈现的更改，需要真实浏览器证据。当更改对具名浏览器作出声明、修复仅在该浏览器中复现的缺陷，或更改浏览器兼容性时，该证据必须来自声明所覆盖的实际浏览器。Chromium 不能替代 iOS Safari 声明，Playwright WebKit 不能证明 Safari 行为。

  明确支持是维护承诺，而非逐更改的证明义务。常规更改使用与其声明相称的证据，无需在合入前证明每个受支持浏览器。在明确支持的浏览器中复现的缺陷仍由 Astryx 负责调查和修复；缺少自动化不会收窄支持，也不构成驳回理由。

- **FR11 — 提高下限属于兼容性工作。** 移除受支持浏览器、将其从完整行为移至降级回退，或移除已记录的回退，需要所有者批准、[`spec:AST-017`](../AST-017/spec.md) 要求的分类与生命周期、用户影响与迁移说明、更新后的生成行、受兼容性声明影响的浏览器的实际浏览器证据，以及证明每个剩余完整支持行和具名明确支持行仍获得完整必需行为的证据。
- **FR12 — 组件规范继承基线。** 组件规范链接 `spec:AST-013`，只记录更严格的要求或明确例外。例外须指明受影响的能力、可观察的缩减、保留的 FR7–FR9 义务、证据、所有者和审查条件。
- **FR13 — 服务器渲染的元素跳过其挂载动画。** 存在于服务器标记中的元素以稳定状态水合，不播放其挂载时播放的动画（入场动画）。该挂载动画仅对客户端在水合后挂载的元素播放，或在仅客户端根中于首次绘制后播放。已水合元素的后续打开、显示和状态转换不在本要求范围内，减少动态效果的行为保持不变。

### 平台支持

- 完整支持：当前 Web Platform Baseline，加上 FR3 中的具名明确支持行。
- 降级回退：Baseline 减两年，满足 FR7–FR9。
- 不支持：低于 Baseline 减两年；Astryx 不作支持承诺。
- 浏览器证据：浏览器自有行为需要真实浏览器证据。针对特定浏览器的声明需要该实际具名浏览器，而非对每次更改的一揽子门槛。

## 当前状态影响

公开指南目前有手写的 Baseline 层级和版本行。对生成的兼容性、明确支持和当前测试覆盖进行三方标注仍属实现工作。当前自动化浏览器覆盖主要使用 Chromium；该覆盖既不定义也不收窄支持。常规更改可凭与其声明相称的证据合入。在明确支持的浏览器中复现的缺陷仍可处理，无论是否存在自动化通道。

`useEntryAnimation` 及其经由的 FieldStatus，根据首次渲染时捕获的首次绘制标志决定是否播放动画。当标记在页面绘制后水合时，水合渲染产生服务器未发送的入场动画类，且该 Hook 的消费者文档称其不支持服务器渲染。

其他已知的 FR9 和 FR13 缺口：CodeBlock 的折叠箭头在页面加载时播放其显示动画；CodeBlock 在渲染期间根据浏览器能力和用户代理检查在 token-span 与 Highlight API 标记之间选择，因此水合渲染可能与服务器标记不同。

## 决策日志

### DEC-1 — 滚动 Baseline 层级加官方浏览器行

**参考：** `spec:AST-013/DEC-1`
**决策者：** `cixzhang`，`2026-09-01`

Astryx 使用当前 Web Platform Baseline 作为完整支持，Baseline 减两年作为降级回退，低于该层级不作承诺。桌面端最新稳定版 Chrome 和最新稳定版 iOS 上的 Safari 始终作为官方支持和测试行包含，独立于生成的 Baseline 覆盖范围，触控呈现另加最新稳定版 Android 上的 Chrome（`spec:AST-094`）。生成的兼容性行与具名官方测试矩阵保持为不同的公开事实。

### DEC-2 — 明确支持不要求每次更改都提供证明

**参考：** `spec:AST-013/DEC-2`
**决策者：** `cixzhang`，`2026-09-02`

DEC-1 的具名浏览器行是明确支持行，而非必需的自动化或逐更改测试矩阵。Astryx 调查并修复在这些浏览器中复现的缺陷，但常规更改无需在合入前证明每个受支持浏览器。当更改作出浏览器特定声明、修复仅在该浏览器中复现的缺陷，或更改兼容性时，需要实际浏览器证据。缺少自动化既不收窄支持，也不构成驳回已复现缺陷的理由。

### DEC-3 — Core 水合为服务器标记；服务器渲染的元素跳过其挂载动画

**参考：** `spec:AST-013/DEC-3`
**决策者：** `cixzhang`，`2026-10-15`

Core 组件在服务器和水合客户端渲染中渲染相同标记，包括客户端组件，且服务器渲染的元素保持稳定，不播放其挂载动画。已拒绝：消费者文档中的“不支持 SSR”例外，因为 FR12 只在组件规范中记录例外。已拒绝：在水合后变为 true 的“已绘制”快照，因为它会为页面加载时存在的元素播放动画。
