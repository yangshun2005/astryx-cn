# 设计规范

设计规范记录由人主导的视觉与交互意图：层级、结构、状态表示、允许的变化以及代表性示例。它们可以描述单个组件，也可以描述跨组件的模式。

## 状态分类

状态记录按变更的驱动方划分。以下仅为三类状态分类记录：

| 记录 | 负责内容 |
| --- | --- |
| [用户状态](user-states.md) | 由人驱动的静止、悬停、按下、聚焦、选中和操作状态 |
| [系统状态](system-states.md) | 由系统驱动的禁用、加载、处理中、状态和瞬时反馈状态 |
| [智能体状态](agentic-states.md) | 由智能体驱动的思考、流式输出、工具执行、等待、同步、检查和渲染状态 |

当某主题具有不同的负责人、审批生命周期、需求集、证据集，或有独立变更的理由时，应创建单独记录。实现机制、公共 API 语法、审计结果和消费者用法不纳入这些记录，改为链接到其规范归属方。

设计规范不负责实现机制、公共 Props 语法、当前审计结果或消费者使用指南。组件和族契约链接到稳定的设计需求 ID，而非复制其理由。

可公开的规范性截图、图表和视觉状态参考位于 `docs/design/assets/<design-id>/` 下。每个被引用的资产记录替代文本、状态、主题/模式、相关时的视口，以及它所展示的决策。生成的审计截图仍属审计证据，而非设计权威。私有设计源保持私有，绝不在此处命名或链接。

新设计规范以 `draft` 开始。首次提升为 `current`、后续变更以及规范性资产更新，均需获得 `.github/ENGOWNERS` 或 `.github/DESIGNOWNERS` 中任一现任成员对其内容的批准（`architecture:knowledge-contracts` DEC-14）。混合 PR 中的非设计 current 记录仍需 ENGOWNER。设计记录在此仓库门禁之外单独列明其内容负责人。

DESIGNOWNER 通过评审或 `/approve-spec <sha>` 批准，与其他负责人一致；在混合 PR 中，其他所有适用的代码或规范负责人组仍为必需。门禁仅决定批准，绝不启用自动合并。

使用 `docs/templates/knowledge/design-spec.md`。
