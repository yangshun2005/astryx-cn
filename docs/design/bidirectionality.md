## 用户意图

无论页面、区域或内容按从左到右还是从右到左流动，用户都应能理解并操作同一个 Astryx 界面。RTL 支持不是对每个像素做机械镜像，而是为当前书写方向保留含义、阅读顺序、空间关系、目标尺寸和交互行为。

## 设计原则

- **DR1 — 保留含义，而非坐标。** RTL 呈现必须保留与 LTR 相同的任务含义和可供性关系。物理上的左/右实现细节不是设计要求，除非内容本身具有物理属性。
- **DR2 — 内容方向与布局方向相互独立。** 页面或区域具有环境方向，而文本、代码、URL、标识符和用户内容可能带有各自的方向。混合方向内容必须保持可读的字符顺序和标点，不得移动到不同的语义槽位。
- **DR3 — 阅读顺序关系遵循行内起始和结束。** 导航、有序推进、主/辅通道、前导/尾随内容以及起始/结束对齐必须遵循所在区域的方向。
- **DR4 — 方向性图形只处理一次。** 含义为上一项、下一项、后退、前进、起始、结束或推进的水平图标或装饰性字形必须镜像或交换一次。Unicode 双向算法已镜像的图形不得再次手动镜像。
- **DR5 — 方向中立和物理内容保持稳定。** 垂直、对称、品牌、媒体、图表、地图、时钟、硬件及其他具有物理含义的内容必须保持不变，除非其特定语义角色具有方向性。将调用方提供的左/右字形几何作为数据暴露的参考示例保留该几何；同一字形用作上一项、下一项或推进提示时则遵循 DR4。
- **DR6 — 交互遵循视觉关系。** 水平键盘移动、拖拽/调整大小计算、轮播或滚动推进、范围导航和侧边放置必须产生 RTL 视觉状态所指示的动作。
- **DR7 — 覆盖层保持附着于其逻辑所有者。** 菜单、对话框、工具提示、弹出框、抽屉及其他分层表面必须保持其起始/结束对齐，并在触发器所在区域内保持与触发器的关系。
- **DR8 — 命中目标跟随可见控件。** 指针或触摸目标在两个方向上都必须保持居中于可见控件，并必须保留组件要求的目标尺寸。镜像不得使可见控件位移、缩小或仅部分可点击。
- **DR9 — 方向变化不得闪现错误关系。** 服务端和首次绘制输出应与文档或区域方向一致。当平台布局能够表达时，方向相关关系不得等待渲染后的 JavaScript 修正。
- **DR10 — 例外需要语义依据，而非便利。** 组件仅当该物理方向承载稳定的用户含义时方可保留物理方向。实现难度、当前 LTR 行为或全 N/A 审计均不构成例外依据。

## 结构与层级

双向性适用于关系，而非单一共享的 DOM 结构。

| 角色             | 用途                                       | 必需关系                                                     |
| ---------------- | ------------------------------------------ | ------------------------------------------------------------ |
| 环境区域         | 建立布局和浏览器文本流方向                 | 后代遵循其 `dir`，除非嵌套内容区域建立了另一方向             |
| 有序序列         | 传达推进或阅读顺序                         | RTL 下第一/上一/起始与最后/下一/结束交换物理侧               |
| 方向性控件       | 沿行内轴移动、显示或指向                   | 图形和行为在恰好一次方向处理后保持一致                       |
| 方向性装饰       | 无交互行为地传达层级或推进                 | 当 UI 角色具有方向性时恰好镜像一次                           |
| 方向中立内容     | 承载独立于行内方向的视觉含义               | 保持其方向                                                   |
| 交互目标         | 接收指针、触摸或键盘输入                   | 保持与可见可供性对齐并保留所需尺寸                           |
| 嵌套双向内容     | 承载方向不同于周围区域的文本               | 保持自身字符顺序、标点和可读隔离                             |

## 状态表示

| 状态                                     | 必需表示                                                         | 允许变化                                     |
| ---------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------- |
| LTR 区域                                 | 行内推进从左侧开始、右侧结束                                     | 组件特定的间距和图形                         |
| RTL 区域                                 | 行内推进从右侧开始、左侧结束                                     | 组件特定的间距和图形                         |
| 显式方向覆盖                             | 所选方向支配子树，即使区域设置通常暗示另一方向                   | 覆盖的测试和产品原因                         |
| 嵌套反向区域                             | 局部内容流改变，但不将区域移动到另一语义槽位                     | 由所属布局契约选择对齐方式                   |
| 混合文本、代码、URL 或标识符             | 字符顺序和结尾标点保持可读                                       | 浏览器双向行为加必要时显式隔离               |
| 手动镜像字形或图标                       | 一次水平镜像或一次配对字形交换                                   | CSS transform 或语义字形对                   |
| Unicode 双向镜像字形                     | 浏览器镜像未更改的字形                                           | 精确字形选择                                 |
| 垂直、对称、品牌或物理图形               | 方向保持不变                                                     | 缩放、颜色和主题处理                         |
| 粗指针控件                               | 目标保持居中并满足组件最小目标尺寸                               | 超出该最小值的不可见命中区域形状             |

## 响应式与输入行为

- **DR11 — 键盘方向在交互时解析。** 左/右行为必须遵循当前渲染区域，包括嵌套区域和运行时方向变化。标签保持语义化（`previous`、`next`、`start`、`end`），而非变为物理左/右指令。
- **DR12 — 指针和触摸几何在质量上与方向无关。** 可见控件、原生输入和有效命中区域在 LTR 和 RTL 下必须在组件声明的容差内共享中心，并必须保留所属组件声明的最小目标尺寸。仅证明居中是不够的。WCAG 2.5.8 目标尺寸归属和例外仍由 AST-020 及组件/组合契约负责。
- **DR13 — 拖拽、调整大小和滚动结果镜像。** 朝逻辑下一项/结束的手势在两个方向上都必须朝逻辑下一项/结束移动。物理增量可以反转，而用户可见动作保持等价。
- **DR14 — 响应式重排保留逻辑归属。** 将内容移入抽屉、面板、溢出菜单或替代布局时，必须保留哪些内容是前导/尾随，以及焦点如何返回其逻辑触发器。

## 无障碍意图

- 无障碍名称描述语义动作，而非物理图标方向。使用"上个月"和"下个月"，而非"左箭头"和"右箭头"。
- DOM `dir` 必须描述浏览器实际区域方向，使文本流、标点、原生控件行为、焦点/导航顺序和无障碍 API 与视觉呈现一致。
- 当浏览器推断无法保持弱标点、数字或 URL 可读时，混合方向用户内容需要显式局部方向或隔离。
- RTL 支持必须保留焦点可见性、键盘可达性、目标尺寸和播报含义。焦点或触摸几何位移的镜像画面不是等价行为。
- 自动化全 N/A 输出不是组件已支持 RTL 的证据。证据策略由 RTL 审计架构单独负责。

## 代表性示例

| 示例                                     | 必需结果                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 层级项之间的面包屑斜杠                   | 作为推进装饰镜像；日期、路径、分数或正文中的 `/` 不镜像                                                      |
| 日历上一项/下一项按钮                    | 按钮交换侧边，箭头指向其动作，语义标签保持上一项/下一项                                                      |
| 粗指针上的复选框、单选按钮和开关         | 原生输入保持居中于可见控件，并在两个方向上保留所属组件的最小目标尺寸                                         |
| 轮播下一项动作                           | 控件放置、图标和滚动增量在逻辑下一项上一致                                                                   |
| 包含 URL 的阿拉伯语句子                  | 阿拉伯语文本按 RTL 流动，URL 保持可读 LTR，标点留在预期内容旁                                                 |
| 原始字形注册表参考示例                   | 调用方提供的左/右几何作为数据保持不变；不暗示方向性控件行为                                                  |
| 品牌标志或照片                           | 不因周围布局为 RTL 而镜像                                                                                    |

## 组件契约链接

当前没有组件记录链接本记录。显式全局路由为组件和模块评审提供匹配的 RTL 关系，无需每个组件反向链接。视觉变更加载图形含义和例外；导航、交互和滚动加载各自的方向性结果及语义例外边界。路由不会使每个字形具有方向性、要求特定实现或解决以下开放问题。

组件、模块和家族契约拥有其局部语义关系：哪些图形是导航提示而非数据、哪些部分是前导/尾随、它们暴露哪些键盘/滚动动作、支持的状态、目标尺寸要求以及证明这些结果的测试。当局部要求或例外需要该关系时，它们引用特定的共享 DR；它们不复制通用 RTL 检查清单或重新定义共享规则。

评审为确切增量解析直接所有者，并仅在其声明范围内应用匹配的共享主张。局部例外需要 DR5/DR10 下一致的语义理由，而非对当前权威的隐式覆盖。运行时/辅助器职责仍归 `architecture:internationalization`；RTL 审计证据和有意 D1 豁免评审仍归 `architecture:rtl-audit-evidence`。

## 决策日志

### DEC-1 — 采用 DR1–DR14 作为共享双向关系

**引用：** `design:bidirectionality/DEC-1`
**决策者：** `nynexman4464`，`2026-10-15`

当组件遵循 DR1–DR14 时，任一方向的读者获得相同的任务含义、阅读顺序和交互结果。审计准入和实现证据仍归各自所有者，以下开放问题保持未决。

## 开放问题

- **OQ1 — 物理方向例外词汇。** 组件是否需要共享的显式方式来记录物理/世界导向图形例外，还是组件局部决策已足够？
- **OQ3 — 混合内容夹具。** 哪些公开安全的混合阿拉伯语/希伯来语加 URL/数字/标点夹具应成为必需的示例故事？
- **OQ4 — 方向变化过渡。** 运行时 `dir` 变化是否应有显式无动画规则，还是组件可在产生的中间关系仍可理解时进行动画？
