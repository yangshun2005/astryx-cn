# 系统状态设计规范

## 用户意图

用户应能在不依赖颜色的情况下区分不可用、等待、处理中、成功、警告、信息提示和错误状态。反馈的醒目程度应与其持续时间和紧急程度相匹配，同时保持周围布局不变。

## 设计原则

- **DR1 — 系统状态保留上下文。** 加载、处理和状态呈现 MUST 保留原组件足够的几何形状和身份特征，让用户理解受影响的内容。
- **DR2 — 状态含义不依赖颜色。** 每种语义状态 MUST 将颜色与图标、标签或其他非颜色信号配对使用。
- **DR3 — 醒目程度随持续时间和紧急程度变化。** 持续性的流内反馈 SHOULD 保持低调，紧凑或紧急的反馈 MAY 使用实心样式，短暂的瞬态反馈 MAY 使用反色浮层。
- **DR4 — 同一含义在各层级间保持一致。** 改变醒目程度 MUST NOT 改变底层的成功、信息、警告或错误含义。
- **DR5 — 忙碌状态不引起布局偏移。** 占位和处理中的呈现 MUST 保持受影响内容的预期尺寸。

## 结构与层级

| 角色         | 用途                         | 必需关系                         |
| ---------- | -------------------------- | ---------------------------- |
| 受影响表面     | 显示被禁用、等待中或报告状态的内容         | 保留足够的几何形状以维持上下文             |
| 进度呈现      | 显示内容或操作尚未完成               | 匹配等待的范围和时长                   |
| 语义指示器     | 传达反馈类别                     | 将颜色与图标、标签或等效提示配对             |
| 辅助消息      | 解释原因、后果或后续操作             | 与受影响表面保持关联                   |
| 醒目程度容器    | 将反馈从流内扩展到瞬态               | 匹配持续时间和紧急程度，不改变含义            |

## 状态呈现

| 状态         | 必需呈现                                         | 允许的变化                              |
| ---------- | -------------------------------------------- | ---------------------------------- |
| 禁用         | 弱化、明确不可用且不可交互；需要时仍可获取原因               | 组件可按其族约定放置原因                     |
| 加载、占位     | 用稳定的骨架或结构占位符代替尚未可用的内容                  | 形状跟随预期内容                         |
| 处理中、原位    | 进度指示器出现时不改变控件尺寸                        | 身份清晰时，指示器可替换或伴随内容                |
| 状态、低调     | 低调的语义表面，将状态颜色与图标或文字结合                   | 用于持续性横幅、字段和流内反馈                  |
| 状态、实心     | 高醒目程度的语义填充，将状态颜色与对比内容结合                | 用于紧凑标签或紧急反馈                      |
| 瞬态浮层      | 在当前内容上方显示短暂的反色表面并自动消失                  | 用于瞬态消息和说明性浮层                     |

## 响应式与输入行为

- **DR6 — 重排后反馈保持关联。** 在窄宽度和方向变化时，辅助消息和进度呈现 MUST 与受影响内容保持关联。
- **DR7 — 瞬态反馈保持可操作。** 响应式布局 MUST NOT 隐藏关闭、暂停或后续操作（当这些操作存在时）。
- **DR8 — 忙碌反馈不依赖动效。** 减少动效模式下 MUST 仍能传达工作正在进行。

## 无障碍意图

用户应能在不依赖颜色感知或动画的情况下识别状态类别、受影响范围和可用的后续操作。禁用原因应无需启用被阻止的操作即可获取。忙碌内容应传达其尚未完成，且不反复打断阅读或焦点。

ARIA 映射、禁用语义、忙碌行为、关闭、时序和实时播报仍由组件和族负责。

## 代表性示例

- 处理值的字段保持其宽度和标签，同时进度指示器占据既定的末端通道。
- 持续性警告使用带图标和消息的低调流内表面。
- 紧急瞬态错误使用更强的醒目程度，但保持相同的错误含义和图标语言。

## 决策日志

尚无仓库设计决策批准此记录。它提炼了公开设计约定 Wiki 中系统驱动的状态和醒目程度词汇，同时将语义和机制留给组件和族。

## 待解决问题

- **OQ1 — 层级选择。** 哪些状态表面具有固定醒目程度，哪些可根据产品上下文或严重程度变化？
- **OQ2 — 处理中区分。** 未完成的表面何时应使用结构占位符，何时应使用原位进度指示器？
- **OQ3 — 瞬态边界。** 哪些瞬态反馈属于此共享词汇，哪些属于专用浮层或通知设计记录？

## 内容边界

本文件定义系统驱动反馈的视觉区分和醒目程度。不定义 Prop 名称、ARIA 属性、加载语义、关闭或时序行为、Token 名称、审计检查或消费方用法。
