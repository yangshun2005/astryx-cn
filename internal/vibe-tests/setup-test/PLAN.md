# 安装测试 — 在既有应用中零损伤引入 Astryx

**状态：** 已集成的准备与测量工具链。此处不提交任何执行器运行结果或模型发现。

## 目标与硬性停止条件

目标是零意外宿主损伤。仅安装 Astryx 不得改变任何既有宿主的圆角、颜色、排版或字体度量、间距、阴影、边框、几何、颜色模式行为或层级顺序。请求的插入或替换只能改变明确指定的表面。

`cosmetic-drift` 仍是有用的诊断标签，但属于失败运行。迭代循环可用失败与各维度增量来改进候选指令；但不授权发布。候选指令只有在单独的最终确认中，于每个受支持的 fixture × prompt × 工具链/模型组合 × 重复次数上**100% 有效运行均分类为 `clean` 且任务特定成功**后，才停止并发布。最终确认不允许任何损坏、噪声、静默损伤或外观结果；缺失探针；可见的变量、对比度、层级、覆盖层或几何回归；逃生舱；或运行后手动编辑。

已分类的随机基础设施故障只能按 `matrix.json` 中预注册的策略重跑。失败尝试仍保留记录。真实的 agent 失败是有效的失败运行，不得通过重试消除。配置的 Codex 组合被上游空回合问题阻塞，因此在该阻塞清除前，最终确认无法启动或声称覆盖所有已配置组合。

定向 `direct` 对照中的损伤是产品缺口。它阻止候选指令发布；不是可接受的限制或文档结果。

## 规范 fixture

每次运行都从 `../fixtures/` 中的共享不可变 fixture 开始：

- `tailwind-v4-control` — 纯 React、Vite 和 Tailwind v4 应用，仅有背景/前景语义。
- `shadcn-tailwind-v4-established` — 既有的 shadcn 风格 Tailwind v4 token 词汇与卡片/表单/表格/状态表面，外加一个 portal 对话框，其 tooltip 和菜单 portal 独立控制。
- `enterprise-scoped-synthetic` — 原创密集应用，具有显式明/暗控制、非 shadcn token、访客设计系统子树，以及一个访客作用域 portal 对话框，其嵌套菜单跨越宿主边界。

`run-setup.mjs` 验证每个 fixture 配方和哈希清单，将 fixture 复制到运行沙箱，绝不写入已提交的 fixture 源。Tailwind v3 仍明确推迟，直到 v4 对照与测量分离。

## 任务

基本安装任务保持不变：仅安装证明（`s0`）、按钮插入（`s1`）、状态替换（`s2`）和选择器替换（`s3`）。`s0` 故意将新证明组件与每个既有宿主探针分开测量。

两个组合任务在不同既有 fixture 上运行：

- `s4`：在既有 Tailwind/shadcn 对话框内放置 Astryx tooltip 和选择器弹出层；
- `s5`：在作用域企业 fixture 的新 Astryx 对话框内放置既有 Tailwind 菜单。

每个任务声明稳定的任务自有 `data-vibe-result` 标记。它们是测量钩子，不是实现提示。评估器用它们验证精确存在、任务完成、键盘可达性、可见性、裁剪、中心命中测试、堆叠顺序，以及——当宿主表面移入 Astryx 对话框时——基线宿主 token 样式。fixture 自有的 `data-vibe-probe` 标记仍是宿主基线，不得改作他用。容器文本保护比较未标记宿主后代的完整规范化文本，同时排除嵌套的探针、结果和替换子树。每个有意替换恰好指定一个 fixture 探针，要求原探针之后不存在，并指定一个保留其宿主文本的结果。其他允许项是 fixture 和字段特定的：宿主允许项只能允许精确位置坐标、强制插入导致的块轴增长，以及——单独声明为 `textInsertionOnly`——容器*获得*的文本，绝不是丢失或重写的文本；覆盖层允许项只能允许精确边界。它们绝不豁免宿主或覆盖层的计算样式、容器宽度或整个相邻探针。

## 既有应用策略试点

另外两个条件探索已具有既定视觉语言的应用的策略。它们是附加且可选的：上述四个对照、其证据及其单元标识不受影响——每个既有阶段保持其精确扩展计数和精确单元 id，策略只能从命名它的新阶段到达——且此试点不改变任何默认、核心或绿地行为。正常的绿地 Astryx 引入与之前完全相同。

| 条件              | 策略                                                                                                                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `host-aligned`    | 既有宿主保持权威。应用拥有一个扩展 neutral 的主题，而非导入库存主题样式表，匹配宿主 body/标题/代码字体及宿主语义颜色和模式对，由应用自身构建确定性地生成。                                                                                                    |
| `guest-contained` | 宿主保留全局 preflight 和 token。不导入 reset，provider 仅包裹新的或迁移的子树，因此设计系统留在该区域内。                                                                                                                                                    |

每个策略条件携带发现指针及其自包含策略文档。策略故意**不**与 `patch:existing-app` 组合：两个策略与该通用配方部分不一致——`host-aligned` 替换库存主题样式表，`guest-contained` 不导入 reset——组合会给执行器矛盾指令并使测量不可读。

两者不是产品对等物，此试点保持的中立性是方法论而非立场性的。`host-aligned` 是既有应用的正常目标：宿主保持权威，整个配方运行在受支持的公开 API 上，其成本是维护——应用拥有的主题必须跟踪宿主自身 token，以及放弃的库存视觉标识。`guest-contained` 是例外机制，适用于全局所有权无法移动、且将设计系统限制在一个嵌套子作用域是工作硬性要求的应用。它目前没有完全受支持的路径：作用域到子树依赖于抑制根属性同步，而没有任何公开 API 暴露该同步，且它付出下文描述的 portal 成本。因此它既作为这两个产品缺口的探针运行，也作为可遵循的配方运行，不是平等的默认选项。保持中立的是测量：试点按失败类别表征两种策略，不输出组合分数，也不排名。

### 此试点暴露的产品缺口

两项发现，均记录而非迁就。评估器对两者都不放宽：受影响规范案例未通过验收，该失败即为结果。

**1. 主题无法退出裸元素规则。** 每个构建主题都会向 `@layer reset` 发出一个散文块——`h1`–`h6`、`p`、`small`、`code`/`pre`，涵盖字族、字号、字重、行高和颜色，外加一条替换宿主边框的 `hr` 规则——按主题名属性 `@scope`。无论主题覆盖哪些 token 都会发出；仅改变单一颜色的主题仍携带完整排版比例。`host-aligned` 还要求在首次绘制前于文档作用域设置主题属性，因此设计系统的比例必然到达既有宿主的裸元素。在裸元素与该比例不同的宿主上，结果是任何受支持配置都无法避免的宿主损伤。要精确匹配宿主，主题需复现宿主整个字体比例，这仅在宿主比例已知且静态时可行。

**2. 无法阻止 provider 声明文档作用域。** 上方无 provider 的 provider 是根 provider，根 provider 将 `data-theme` 和 `data-astryx-theme` 同步到文档元素。由于主题 CSS 按该属性 `@scope`，同步正是让主题 token 到达 provider 子树外 portal 内容的原因。provider 的公开 props 是 `theme`、`mode` 和 `children`；均无法退出。目前最强机制是在挂载后移除该属性并用 `MutationObserver` 保持移除——这是变通方法，不是配置——且它牺牲 body-portal 表面的主题化。规范 `guest-contained` 实现携带该变通方法，标记为变通方法，并在调用点记录权衡。

缺口 1 最严重：它意味着只要宿主渲染裸散文元素，"既有宿主在排版上保持权威"目前就无法通过受支持配置实现。它现在是唯一阻止 `host-aligned` 通过验收的因素，且是真实产品缺口而非评估器伪影。`guest-contained` 确实达到验收，代价是缺口 2 的 portal 成本——但验收是测量对宿主损伤的裁决，不是产品推荐：它通过缺口 2 的不受支持变通方法达到，因此解读是缺口 1 阻塞受支持策略，而缺口 2 是例外策略的代价。

### 此试点发现的评估器缺陷，已在此修正

`astryx theme build` 对任何具有 `light-dark()` 值的主题发出 `:root { color-scheme: light dark; }`，配以 `html[data-theme="light"] { color-scheme: light; }` 及其暗色孪生。这些规则实现模式支持，但 `dark-mode-disabled` 逃生舱按词法匹配裸 `color-scheme: light`，因此任何发布构建主题的应用都会触发检查——仅仅重新缩进自身亮色臂的既有宿主也会。这是评估器缺陷而非产品缺口，因此修正而非记录。

`color-scheme` 现在按语义读取。单模式声明仅作为**配对模式臂**豁免：其自身选择器和 at-rule 将其作用域限定为恰好一个模式，其值是该同一模式，且互补臂在同一文件的同一作用域存在。生成文件不作为类别忽略——声称 `@generated by astryx theme build` 头的文件会对照该声明检查（声明的源必须是沙箱内仍存在的相对路径，且产物必须位于该构建写入的位置），同一变更中丢失模式行的文件完全无豁免，且所有其他逃生舱在生成产物内照常扫描。强制宿主为固定方案、重写一对中的一个臂、丢弃一个臂，以及在真实配对旁固定 `:root` 仍全部失败。其他阶段的评估器行为不变。

### 首次试点运行发现的问题，已在此修正

首次操作员运行（80 个单元中的 10 个：一个组合、一次重复）又暴露五个评估器缺陷和一个指令缺陷。六个均在此修正；无一放宽评估器对宿主损伤的认定。

**1. `hardcoded-important` 将散文读作代码。** 检查对宿主源文件的每一新增行匹配 `/!\s*important/i`。十个单元中三个因 JSDoc 注释失败——`guest-contained` 指引告诉执行器不要用 `!important` 掩盖 portal 权衡，执行器在其选择的变通方法旁写下该理由，检查因这句话使运行失败。该标志现在通过解析而非匹配发现：样式表经 postcss，其中 `Declaration.important` 是解析器自身的答案，注释是 `Comment` 节点；脚本经 TypeScript 解析器，其中注释是琐碎内容，仅检查字符串和模板字面量；HTML、Vue 和 Svelte 拆分为 `<style>` 块、`style` 属性和 `<script>` 块。忽略注释和散文不会打开通路：字面量在包含携带该标志的声明、是真实 CSS 属性的值（取自 `CSSStyleDeclaration` 而非手写列表）、或是 `setProperty` 的优先级参数（旧扫描完全看不到）时计数。无法解析的样式表回退到仅跳过注释和引号字符串的扫描器。变异证明覆盖样式对象、JSX 内联样式、CSS-in-JS 模板、插值声明、注入的样式表字符串、`cssText` 写入、运行时 `setProperty`，以及直接写在否认它的注释下方——且同一行——的覆盖。

**2. `s5` 契约没有为任务强制插入留出允许项。** `s5` 要求新 Astryx 对话框，因此执行器必须在宿主页面放置触发器。两个 `s5` 单元都向宿主外壳添加了一个块，且都报告相同的八个回归——`height`、`geometry.height`、`geometry.bottom` 和 `text`，明暗各一——因为做了任务要求的事。契约现在恰好允许这些，且仅在该探针上：外壳高度和高度移动的两个几何字段，加上外壳*获得*的文本。`textInsertionOnly` 故意不同于将 `text` 放入 `fields`：每个基线词必须仍按原顺序存在，因此可增长的容器仍不能丢失或重写宿主自身文案。其他不动——外壳位置、宽度、其上每个计算样式，以及每个其他探针保持精确，且 `text` 已从可豁免宿主字段中完全移除，因此任何契约都无法让比较通过。规范浏览器案例证明强制重排通过，同一测量运行上的变异证明证明附近颜色、字体、圆角、阴影或内边距、外壳自身宽度或位置、另一探针的几何或颜色，以及任何丢失的宿主文案仍全部失败。

同一缺口存在于内一层容器。`s5` 强制恰好一个可见 `astryx-dialog-trigger`，且此 fixture 为访客设计系统内容声明访客子树，因此触发器属于那里——两个独立重复也放在那里。两者都将 `guest-boundary` 从 296px 增长到 409px，在两种方案中移动其高度和高度移动的两个几何字段。这是插入自身的几何，因此契约现在也允许该探针上的这三个字段。它比外壳的更窄：触发器是任务自有的，因此边界的受保护文本已排除它，允许项完全不命名文本豁免。边界宽度、位置、每个计算样式，以及每个其他探针保持精确，以同样方式证明——一个规范浏览器案例将触发器插入访客子树并测量真实应用，以及该测量运行上的变异证明，针对颜色、字体、边界宽度、边界移动、相邻探针高度，以及边界获得或丢失的宿主文案。

**3. `gitignore-modified` 是对的；指令错了。** 两个 `host-aligned` 单元将生成的主题产物添加到 `.gitignore` 并触发逃生舱失败。逃生舱在此或任何地方都未削弱：执行器不得在执行基线后重写忽略规则。缺失的是指令。指引说主题确定性构建，从未说输出是跟踪文件，而此应用自身历史提交其生成主题产物。`host-aligned` 指引现在要求提交主题源及构建从中写入的一切，禁止将该输出添加到 `.gitignore`，并回答两个执行器实际提出的论点——重新生成的文件无需跟踪。那两个单元仍是失败：它们是指令失败和 agent 失败，不是评估器缺陷，必须在修正后的指引下重跑而非重新评分。

**4. 测量改变了它所测量的沙箱。** _历史：故障真实且成立，但此处描述的修复在任何部分发布前已被**下文第 5 项取代**。链接镜像的 `node_modules` 不是当前构造——阅读第 5 项了解构建根实际做什么。_ 测量器在 agent 自己的沙箱内运行 `pnpm build`。该树是经证实的产物——运行器消化了那些字节，完整性读取它们，任何重新测量或恢复都必须再次读取它们——而构建覆盖了它：`prebuild` 在执行器副本上重新生成应用拥有的主题，`vite build` 写入 `dist/`，CLI 追加其调用日志，打包器缓存到 `node_modules`。失败的构建留下相同碎片，因此已测量单元不再哈希到自身摘要，其证据无法重新推导。构建现在在一次性副本中运行。符号链接作为符号链接复现，因此解析不变，且——在此初版中，已被取代——`node_modules` 以每包一个链接镜像而非复制或硬链接，理由是构建重写的硬链接文件会写穿到原始 inode，而镜像目录会在副本中捕获写入。构建根在每条退出路径上移除，包括抛出的测量。测试在真实测量前后取沙箱的完整字节和 mtime 清单，并要求成功构建、失败构建和抛出构建均相同；变异证明运行旧的原地构建并显示清单报告它。测量输出不变：稳定 fixture id、无私有路径，构建根与它们一同脱敏。测试在真实测量前后取沙箱的完整字节和 mtime 清单，并要求成功构建、失败构建和抛出构建均相同；变异证明运行旧的原地构建并显示清单报告它。测量输出不变：稳定 fixture id、无私有路径，构建根与它们一同脱敏。

**5. 构建根镜像了虚拟存储而非复制它。** 构建根初版将每个 `node_modules` 条目符号链接到原始，对 pnpm 安装而言意味着 `.pnpm`——持有每个真实包树的虚拟存储——是指回沙箱的链接。通过符号链接写入会写到其目标，因此副本中的安装或重建重写了沙箱自身存储，顶层包链接也解析到其中。副本现在是真实副本：文件用 `cp -a --reflink=auto` 复制，文件系统支持时写时复制共享区段，不支持时字节复制，且绝不硬链接——副本中重写的硬链接文件会重写原始 inode。符号链接保留其目标文本，因此 `is-odd -> .pnpm/is-odd@3.0.1/node_modules/is-odd` 及存储内每个依赖链接现在在副本内解析；会到达沙箱的绝对链接重定向到副本，而指向别处工作区包的链接保持不变。`verifyWorkspaceIsolation` 从完成的副本重新推导声明——每个符号链接解析，inode 与原始比较——测量器在任何构建前运行它。测试用真实 `pnpm install` 构建 fixture，然后要求沙箱完整清单（含虚拟存储）在成功构建、失败构建，以及副本中完全删除并重建 `.pnpm` 的安装后字节相同；纯 Node 复制器以同样方式测试。变异恢复旧镜像并显示沙箱被写穿且隔离检查命名它，硬链接副本被同一检查捕获。

**6. 报告将四种不同失败拼写相同。** `verdict` 将测量到的宿主损伤、逃生舱、任务失败和损坏的测量折叠为 `silent-damage`，这对门禁正确但对报告无用：从注释误读的 `!important` 和重绘的宿主以同一个词
