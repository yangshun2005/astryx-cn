## 策略：宿主对齐式采用

此应用已有成熟的视觉语言。当宿主应用在排版和颜色上保持权威、设计系统应融入其中时，采用此策略。

这是成熟应用的常规目标，下文完整方案均受支持：用已发布的主题 API 构建应用自有主题，按文档使用 Provider，其中不含任何不受支持的行为。其代价真实存在且不隐瞒——应用自有主题必须随宿主自身 token 变化而维护，并有意放弃设计系统的默认视觉标识——但这是维护成本，不是能力缺失。

另一项已记录的策略——访客容器式采用——对于只想保持自身外观的应用而言，并非本策略的替代方案。它适用于更窄的场景：必须将设计系统限制在单个子树内。该策略在单独文档中描述。

### 开始之前——四条非判断性规则

本文档其余内容是需要你自行推理判断的。以下四条不是：

1. **提交生成的主题产物。绝不要将其加入 `.gitignore`。** 确定性构建步骤说明输出可复现，而非停止跟踪它的理由。详见下文。
2. **不要导入默认主题样式表**，也不要导入 `@astryxdesign/core/tailwind-theme.css`。详见下文。
3. **保持 `.gitignore` 原样。** 若构建写入已被忽略的位置，改变写入位置。
4. **若将现有宿主 UI 移入 Astryx 浮层，被移动的子树必须保留原先限定其 token 的宿主边界。** 不是 token 值——而是边界本身：宿主自身 CSS 所依据的属性、类或 id。改为复制颜色是缺陷，且会被检测。详见下文，包括如何找到该边界。

### 拥有主题；不要导入默认主题

**不要**导入默认主题样式表，如 `@astryxdesign/theme-neutral/theme.css`。构建应用专属主题，扩展中性主题并仅覆盖宿主已定义的内容：

- body、标题和代码/等宽字体族，与宿主自身的字体栈一致；
- 宿主的语义颜色，定义为明确的亮色和暗色配对，使两种模式都解析为宿主现有值。

将该主题构建为应用自身构建的确定性步骤——相同输入必须始终产生相同 CSS——并导入生成的样式表和构建后的主题对象。不要在每次启动时于运行时生成主题。

### 提交主题源文件**及**其生成输出

主题源文件及构建从中写出的一切都是项目文件，都应纳入版本控制：

- 提交主题源文件（例如 `src/hostTheme.ts`）；
- 提交生成的样式表及构建在其旁输出的每个同级产物（例如 `src/hostaligned.css` 及其生成的类型和变体文件）。

**不要**将生成输出加入 `.gitignore`。确定性构建步骤说明输出可复现，而非停止跟踪它的理由：此应用自身历史将生成的主题产物保留在树中，审查者必须能看到主题变更实际产生的 CSS，而在 `predev`/`prebuild` 时重新生成文件的构建仍将已提交副本作为可审查记录。忽略输出还会隐藏漂移或手工编辑的产物，而这正是已提交副本要捕获的问题。

若构建将产物写入已被忽略的位置，改变写入位置，而非改变忽略规则。保持 `.gitignore` 原样。

### 保持宿主的级联

- 在宿主已有 `@import 'tailwindcss';` 的位置保留它，并在其**上方**声明层顺序，使输出顺序显式：

  ```css
  @layer reset, theme, base, astryx-base, astryx-theme, components, utilities;

  @import 'tailwindcss';
  @import '@astryxdesign/core/reset.css';
  @import '@astryxdesign/core/astryx.css';
  /* 应用自身生成的主题，而非默认 theme.css */
  @import './<theme-name>.css';
  ```

  构建以**主题**命名输出，而非源文件，并写入源文件旁：在 `src/hostTheme.ts` 中声明的名为 `hostaligned` 的主题生成 `src/hostaligned.css`。导入该文件。

- 在**输出**的 CSS 中验证层顺序，而非源码顺序。构建步骤可能重排或提升导入。
- **不要**导入 `@astryxdesign/core/tailwind-theme.css`。它有意映射常见颜色、圆角、阴影、字体和间距名称，会将宿主的 Tailwind 词汇交给设计系统。

### 在首次绘制前设置主题属性

`data-astryx-theme` 必须在首次绘制前存在于文档元素上，而非由水合后的 effect 写入。否则首帧无主题，页面明显重排。在服务端渲染标记或 `<head>` 中的阻塞内联脚本中设置它。

保持 `data-theme` 和 `color-scheme` 与宿主自身的模式控制同步。宿主拥有亮/暗切换；设计系统跟随它。绝不要替换或禁用宿主的模式控制。

### 裸元素规则——了解主题带来的影响

构建后的主题总会为裸文本元素输出规则——`h1`–`h6`、`p`、`small`、`code`/`pre`，涵盖字体族、大小、字重、行高和颜色，以及 `hr`（其边框被完全替换）。无论主题覆盖什么，这些规则都会输出；只改一个颜色的主题仍携带完整排版比例。它们以零特异性落入 `@layer reset`，因此任何宿主类都胜过它们，但无类的宿主元素则不然。

由于此策略将主题属性置于文档作用域，这些规则会触及宿主自身的裸元素。采用此策略前，检查宿主实际渲染的无类内容。若任何裸文本元素的解析字体族、大小、字重、行高、字距或颜色会改变——或任何 `hr` 的边框——主题必须为这些 token 重述宿主的值，使结果像素一致。近似匹配即宿主损坏。

若宿主的裸元素样式无法精确复现——例如因区域而异——此策略目前对该宿主不安全，且没有受支持的方式抑制输出的文本规则。报告此情况，而非用全局覆盖或 `!important` 掩盖。

### 置于设计系统浮层内的宿主 UI

任务可能要求将宿主标记组合在**设计系统浮层内**——例如从对话框内打开宿主自己的菜单。将宿主标记移入浮层会改变其在 DOM 中的位置，而成熟应用的表面通常由限定在 DOM 某区域的 CSS 自定义属性绘制，而非全局定义：

```css
[data-app-region='settings'] {
  --panel: #f5f3ff;
  --border: #c4b5fd;
}
```

曾是该区域后代的宿主表面会解析这些值。在别处声明的浮层内渲染的相同标记不再是其后代，因此**相同的类**改为解析为应用的全局值，表面悄然变色。将元素提升到顶层无济于事：`popover` 和 `<dialog>` 改变元素绘制位置，而非继承来源。

因此，当宿主标记移入浮层时，**将边界随标记一起携带**。找到边界，放回被移动的子树，并验证。

**找到它。** 不要猜测，也不要假设它与承载亮/暗的是同一个钩子——应用常有一个属性用于模式，另一个用于区域调色板，只复制模式钩子会遗漏调色板。从 token 反向追溯：

1. 在宿主样式表中，找到表面颜色的实际来源。读取元素上已有的类——`bg-panel`、`border-border`、`text-foreground`——并记下其背后的自定义属性。
2. 在样式表中搜索**重新声明**这些属性的每条规则。一条会是 `:root` 或等价物；那是全局集。其他任何一条都是区域。
3. 该区域规则的选择器就是边界。它随宿主命名——属性、类或 id。
4. 从元素本身向上追溯，确认表面原始位置在其内。边界常已在元素上，此时移动元素即移动边界——而移动时丢弃该属性正是错误所在。

**应用它。** 将相同边界放在被移动的子树——相同属性，拼写相同——使宿主自身规则如旧解析。若宿主分别限定亮色和暗色，也携带宿主的模式信号。其余保持宿主的标记、类和 token 不变。将颜色重述为字面量不是同样的修复：它复制了宿主可更改的值，并在宿主下次调整调色板时悄然漂移。

**验证。** 在**两种**模式下，比较重定位表面的计算背景、边框和文本颜色与原始位置的同一宿主表面。必须完全匹配。近似匹配即宿主损坏。测量同时检查边界和颜色，并分别报告：`host-boundary` 失败意味着被移动的子树脱离了宿主的 token 区域，重述多少颜色都无法清除。

### 检查渲染后的应用

在两种模式下**构建并**查看应用。级联、继承颜色和字体度量变化都能干净编译。
