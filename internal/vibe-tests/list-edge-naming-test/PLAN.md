# List 边缘命名氛围测试

**状态：** 临时性 · 第 1–3 轮已完成 · 建议已随 PR #7592 发布
**相关：** [`../README.md`](../README.md)（Checker Protocol）、[API 仲裁](https://github.com/meta/astryx/wiki/API-Arbitration)、[设计氛围测试](https://github.com/meta/astryx/wiki/Designing-Vibe-Tests)、[PR #7592](https://github.com/meta/astryx/pull/7592)

---

## 1. 问题

[PR #7592](https://github.com/meta/astryx/pull/7592) 为 `List` 提供了一个 prop，用于决定每行文本、高亮和分隔线相对于列表两侧以及外围 `Card`、`Section` 或 `Dialog` 的位置。共有四种外观：

| 外观        | 行文本                                    | 高亮和分隔线                                               |
| ----------- | ----------------------------------------- | ---------------------------------------------------------- |
| 1（默认）   | 距列表两侧一小段距离                      | 横跨列表，略超出文本                                       |
| 2           | 位于列表两侧，与标题对齐                  | 止于文本                                                   |
| 3           | 与标题对齐                                | 略超出文本，但未触及容器边框                               |
| 4           | 与标题对齐                                | 触及容器边框，类似表格行                                   |

**该 prop 及其四个值应该叫什么？** 第 1、2 轮测试了 PR 的初始命名 `edge` 及 `inset · flush · outset · bleed`，并与备选方案对比。第 3 轮测试其最终发布的命名 `padded · flush · outset · bleed`，与已发布的 API 以及完全无 API 的情况对比。

## 2. 设计

按[设计氛围测试](https://github.com/meta/astryx/wiki/Designing-Vibe-Tests)的四要素摄入。

**目标与度量。** 告知朴素 agent 布局需求，但不告知任何 prop 或值名称。按正确性、虚构的 prop 或样式、直接性、置信度校准评分。平局时：误读和虚构 prop 更少者优先，其次用词更平实者优先。

**三个探针。**

| 探针   | agent 获得的内容                                     | 度量内容                                      |
| ------ | ---------------------------------------------------- | --------------------------------------------- |
| 使用   | 其分支的参考文档和一个布局提示                       | 能否从文档中选对值？                          |
| 回忆   | 描述四种外观但不提及任何 API 的文档                  | 期望什么 API？一个 prop 还是多个？            |
| 阅读   | 无文档，仅 `Card` 中使用了一个值的代码               | 仅凭名称能否预测渲染效果？                    |

**使用测试组。** [`prompts.json`](prompts.json) 中有七个提示。均未提及 prop、值，或 padding、inset、edge、margin、align 等词。

|     | 布局                                                                             | 正确外观                                 |
| --- | -------------------------------------------------------------------------------- | ---------------------------------------- |
| p1  | 页面标题下的静态列表，带分隔线，无卡片                                           | 2                                        |
| p2  | 卡片中的静态列表，线条触及卡片边框                                               | 4                                        |
| p3  | 卡片中的静态列表，线条未触及边框                                                 | 2                                        |
| p4  | 卡片中可点击的文件夹，高亮留有空间且不触及边框                                   | 3                                        |
| p5  | 卡片中可点击的菜单，高亮触及卡片两侧                                             | 4                                        |
| p6  | 最近文件弹窗，无需对齐的对象                                                     | **不设置**（阴性对照）                   |
| p7  | 标题下的侧边栏列表，无卡片，文本对齐且高亮留有空间                               | **无单一值可同时满足**（冲突）           |

**分支。**

| 分支          | 轮次 | prop                                                | 外观 1   | 外观 2  | 外观 3     | 外观 4  |
| ------------- | ---- | --------------------------------------------------- | -------- | ------- | ---------- | ------- |
| A             | 1    | `edge`                                              | `inset`  | `flush` | `outset`   | `bleed` |
| B             | 1    | `edge`                                              | `padded` | `flush` | `hanging`  | `bleed` |
| C             | 2    | `rowAlignment`                                      | `inset`  | `flush` | `outset`   | `bleed` |
| D             | 3    | `edge`                                              | `padded` | `flush` | `outset`   | `bleed` |
| 双名称        | 3    | `edge`，加上已弃用的 `edgeCompensation="inline"`    | `padded` | `flush` | `outset`   | `bleed` |
| 主基线        | 3    | `edgeCompensation`                                  | 未设置   | —       | `'inline'` | —       |
| 自然触达      | 3    | 无                                                  | —        | —       | —          | —       |

分支 B 交换了两个最可能误导的名称：`outset` 较为罕见，而 `inset` 在某些平台上已指代另一种列表。分支 C 是第 1 轮中最常被回忆起的 prop 名称，按计划在第 2 轮加入。

第 3 轮增加了评审要求的三条分支，每条均在相同的七个提示上运行：

- **主基线：** 已发布的 `List`，其唯一的边缘 prop 是 `edgeCompensation="inline"`（外观 3）。其 API 无法产生外观 2 和 4，因此 p1、p2、p3、p5 度量 agent 在 API 不足时的行为。
- **自然触达：** 完全没有边缘 API，也没有反模式章节，因此没有任何内容引导 agent 远离被度量的变通方案。文档仅描述默认外观。
- **双名称：** 发布的名称加上已弃用的 `edgeCompensation`，即兼容窗口期文档的呈现方式。旧名称是否会吸引使用？
- **分支 D**，仅发布的名称，是双名称分支对比的对照。它也是发布名称集作为整体的首次使用运行。

**编排。** 91 个隔离 agent，每个任务一个，全部在同一模型的同一设置下运行：第 1 轮有 14 个使用、6 个回忆、10 个阅读 agent；第 2 轮有 7 个使用（分支 C）和 26 个阅读 agent；第 3 轮有 28 个使用 agent（四个分支各七个提示）。第 2 轮的阅读探针增加了第 1 轮拆分或样本不足的样本，尝试两个 prop 名称，并增加了一个显示编辑器悬停时类型的条件。脚本化检查器（[`check.mjs`](check.mjs)）为每个值选择和多项选择答案评分。一个评审 agent 并排查看所有分支，按评分标准为第 1 轮的使用回复评分；第 2、3 轮由检查器评分，第 3 轮的变通方案从每个回复的代码和注释中读取。

### 公平性（Checker Protocol）

| 不变量                        | 如何遵守                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| §1 公平评估者                 | 检查器对每个分支应用同一规则。评审按同一评分标准并排查看所有分支为第 1 轮评分。由于值名称暴露了分支，盲评不可能，因此告知评审按评分标准而非个人偏好评分，并先审计文档一致性。未发现不一致                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| §2 仅 SUT 变化                | [`gen-docs.mjs`](gen-docs.mjs) 从同一模板渲染每个分支，除非分支 B、C、D 将其不同名称映射回去后与分支 A 逐字节相等（各 507 词），否则失败；双名称文档去掉其弃用行和段落后等于分支 D。主基线和自然触达文档仅在其边缘章节不同，即被测系统：主基线的第二个示例位于 `Card` 中，因为其唯一值需要卡片，自然触达则无反模式。正文从不使用呼应某分支名称的词（pad、inset、inside、outset、outside、hang），回忆文档的正文从不使用会命名该 prop 的词 |
| §3 绝不泄露答案               | 真实答案存于 `prompts.json`，从未到达生成 agent。提示已扫描 padding、inset、edge、margin、align 和 indent                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| §4 代表性环境                 | 参考文档是消费者 agent 所读的内容。阅读探针是评审在代码中看到的内容，含或不含编辑器的类型悬停                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| §5 无上下文                   | 每个 agent 全新启动，仅收到其自身任务文件的精确路径，所在目录无法列出。91 个测试 agent 的日志均显示恰好一次工具调用：读取该文件                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## 3. 发现

### 3.1 有文档时，名称不改变 agent 的构建结果

**18 个计分使用提示在三个分支中全部正确**，无虚构 prop，无自定义样式。三个 p6 agent 均未设置该 prop。三个 p7 agent 均看出外观 3 需要容器：分支 A 和 C 选择外观 2 并称高亮会很紧（置信度 2/5），分支 B 将标题和列表包裹在 `Section` 中（3/5）。

与此前的命名测试一样，一旦 API 有文档，agent 按外观描述（"类似表格行"、"不触及那些边框"）而非名称来选择。以下内容均关于 agent 的期望和阅读方式。

### 3.2 agent 期望一个 prop 带四个值

全部六个回忆 agent 都写出了一个 prop 带四个值。无人写布尔值，且六人均主动拒绝：是/否开关无法在四种外观中选择，多个开关允许"同时开启"等无意义的组合。

### 3.3 `inset` 在代码中被误读；`padded` 阅读效果更好

| 值       | 裸代码    | 含编辑器类型 |
| -------- | --------- | ------------ |
| `inset`  | **0/9**   | 2/3          |
| `padded` | 5/9       | 3/3          |

每个裸 `inset` 读者都称文本与标题对齐，这与外观 1 的行为相反。他们将其读作"inset 在卡片的 padding 内"（第 1 轮：_"'inset' 暗示列表位于卡片的 padding 内，因此行文本与标题对齐"_）。四个误读的 `padded` 读者通过另一路径犯了相同的放置错误：他们假设行围绕其 padding 向外扩展，因此文本保持在标题行上。

回忆指向相反方向：六个回忆 agent 中有五个将外观 1 命名为 `inset`，三个为外观 3 选择 `outset`，因为它与 `inset` 配对。第六个选择 `padded` 仅因其 prop 已名为 `rowInset`，且它精确产出了 `padded · flush · outset · bleed`。agent 猜测 `inset`，但会误读它。

### 3.4 `outset` 和 `bleed` 每次都被正确阅读

`outset` 4/4、`hanging` 2/2、`bleed` 3/3 仅凭代码即完全正确。在回忆中，`outset` 在六个样本中的四个命名了外观 3（`hanging` 和 `bleed` 各一次）。四个回忆 agent 考虑过 `hang` 或 `hanging` 并拒绝：两个因其为排版术语（悬挂标点、悬挂缩进），两个因 `outset` 与 `inset` 配对。`bleed` 在四个样本中命名了外观 4（`edgeToEdge` 和 `fullBleed` 各一次）。

### 3.5 `flush` 是人人都会想到的，但其高亮是猜测

全部六个回忆 agent 将外观 2 命名为 `flush`，每个使用 agent 都正确应用了它。仅凭代码，三个读者都将文本放在正确位置，但**无人**将高亮放在文本处：一个将其略超出文本，两个将其和分隔线延伸至卡片边框。文档必须明确说明外观 2 的高亮和分隔线止于文本。

### 3.6 agent 猜测对齐风格的 prop 名称，但效果并不更好

回忆产生了 `rowAlignment` 3、`rowAlign` 1、`rowInset` 1、`edge` 1。但分支 C（`rowAlignment`）在使用中与 `edge` 得分相同（6/6），阅读效果也不更好：

| 值       | `edge` | `rowAlignment` |
| -------- | ------ | -------------- |
| `inset`  | 0/6    | 0/3            |
| `padded` | 4/6    | 1/3            |
| `outset` | 2/2    | 2/2            |
| `bleed`  | 1/1    | 2/2            |

回忆 agent 自己拒绝了裸 `align` 和 `alignment`，因其指左、中、右文本对齐。在此代码库中，`Item` 已有 `align` prop 用于其起始和结束内容的垂直对齐，因此 `List` 上的 `rowAlignment` 会与一个无关的 `align` 并列。

### 3.7 无该 prop 时，agent 会变通；弃用名称未吸引使用

| 分支              | 正确外观（其 API 可达的提示）          | 自定义样式 | 写入弃用 prop | 置信度，p1–p5                              |
| ----------------- | -------------------------------------- | ---------- | ------------- | ------------------------------------------ |
| D（发布名称）     | 6/6                                    | 0/7        | —             | 4/5                                        |
| 双名称            | 6/6                                    | 0/7        | 0/7           | 4–5/5                                      |
| 主基线            | 2/2（p4、p6）                          | 0/7        | —             | p4 为 4/5；API 不足处为 2–3/5              |
| 自然触达          | 1/1（p6）                              | 5/7        | —             | 1–2/5                                      |

- **发布名称。** 分支 D 每次正确使用发布名称集，与分支 A、B、C 相同。其 p7 agent 选择外观 2 并指出高亮很紧，与分支 A、C 相同。
- **双名称。** 无 agent 写入 `edgeCompensation`；一个称其故意省略弃用 prop。其 p7 agent 将标题和列表包裹在 `Section` 中并使用 `outset`，与第 1 轮分支 B 相同。
- **主基线。** 对于其 API 无法产生的四种布局（p1、p2、p3、p5），每个 agent 仍写入 `edgeCompensation="inline"`，将 p1 包裹在 `Section` 中以使其生效。无人添加自定义样式，四人均称布局无法实现：线条超出文本，或高亮未触及卡片边框。一个要求"类似 `edgeCompensation=\"bleed\"` 的东西"。六个布局中四个发布后明显错误，agent 知道这一点。
- **自然触达。** 每个对齐提示（p1–p5）都以变通方案告终。四个 agent 用猜测的像素值（12px、16px）偏移列表或标题，一个放弃 `List` 改用手工构建的 `<ul>` 并自带边框。每个都写明数字是猜测。p7 agent 将标题放入 `List` 的 `header` 槽，希望它能对齐。

### 3.8 使用探针暴露的文档缺口（非命名）

1. **哪些容器算数。** 三个 p6 agent 都问弹窗是否算作外观 3 和 4 的容器。
2. **起始内容是否算作文本。** 三个 p4 agent 都不确定 `startContent` 中的图标是与标题对齐还是标签对齐。
3. **侧边栏。** 无外观能在无容器的情况下对齐文本并保留高亮空间。三个 p7 agent 中一个使用了 `Section` 包裹；另外两个考虑过但因文档未说明 `Section` 是否看起来像盒子而放弃。文档可以展示该模式。

## 4. 建议

**保留 `edge` 和一个 prop 带四个值。将外观 1 从 `inset` 重命名为 `padded`。保留 `flush`、`outset` 和 `bleed`。** 已应用于 [PR #7592](https://github.com/meta/astryx/pull/7592)，List 文档涵盖 §3.5 和 §3.8 中的三个缺口。

- 一个 prop 带四个值，因为回忆 6/6 产出它，且各外观互斥（§3.2）。
- `edge`，因为 agent 猜测的替代方案效果并不更好且与 `Item` 的 `align` 冲突（§3.6），且 `edge` 匹配现有的边缘补偿词汇。
- 外观 1 用 `padded`，因为 `inset` 从代码中被误读 0/9 而 `padded` 为 5/9；仅当编辑器显示完整类型时差距才缩小至 2/3 对 3/3（§3.3）。代价是回忆 agent 喜欢的 `inset`/`outset` 配对。
- `outset` 和 `bleed`，因为它们每次都被正确阅读且回忆率最高（§3.4）。
- `flush`，因为人人都会想到它，文档需说明其高亮和分隔线止于何处（§3.5）。

第 3 轮支持此建议。发布名称集在使用中得分 6/6。与弃用名称并列时，无 agent 选择旧名称。
